## Entries

- `coderfleet/server/telegram_bridge.py` — Telegram long-poll bridge: command routing, topic-per-project registration, broadcast, ASR. All state mutations (offset, per-chat sections, topic registry) must go through `_update_state`/`_set_chat_entry` — a synchronous read-modify-write with no `await` inside the mutator, so it's atomic under the event loop; a separate read-then-write reintroduces the race that `_advance_offset` was written to close (long-poll offset writeback must never clobber a `notify_task` mapping persisted while the poll was suspended). `_ensure_topic` concurrent-create resolves by "first registrant in the state file wins" — a thread created after losing the race is dropped, never re-registered. `is_configured()` is true if `token` and EITHER `chat_ids` OR `topic_group_id` is set — do not require both; group membership is its own trust boundary. `poll_timeout` is 25s, not 50s — proxied long-poll tunnels commonly kill idle connections at 30s+, so a 50s window causes a `ReadTimeout` every round; if you touch the poll loop, keep this under ~28s. `_advance_offset` runs unconditionally after each update regardless of handler success — a poison message must not stall the queue. `_hint_topic_permission_once`'s one-time flag is only persisted after the hint send succeeds — a failed send must retry next round, not burn the one-shot. On unknown/invalid references (expired conversation button, reply to an untracked message, a deleted topic thread) the handler must reject/warn explicitly and never silently fall back to "most recent" or a stale default — this class of bug recurred across #46-49 and #51-53 review passes. Broadcast excerpts are extracted by the bridge itself, not reused from the Digest's LLM summary — the Digest summary strips code blocks to `[代码略]` and truncates at 600 chars, which is unacceptable for a code-review broadcast; the bridge's own excerpt keeps code, caps at 3000 chars, with the full message still bounded by Telegram's 4096 hard limit.

- `coderfleet/server/main.py` — FastAPI app defining all REST endpoints and WebSocket terminal handlers; wires the Telegram bridge and usage-polling loops at startup. `create_task` resolves account/project by fixed precedence — `account` param > `project` (mounted-path match) > `type` > first idle account — and must check `scheduler.conversation_queue_full(req.conversation_id)` before calling `scheduler.submit`; `MAX_PENDING_PER_CONV` is imported from `scheduler.py`, never redefined locally, since a prior local recount in main.py drifted out of sync with an equivalent check in `telegram_bridge.py` (fixed in `b315ea7`). `reconcile_tasks_on_startup` requires `telegram_bridge.start_polling()` to run before `scheduler.reconcile_running_tasks()`, so the bridge is wired before any reconciled task can complete and try to notify through it. Both WebSocket terminal handlers (`project_terminal`, `conversation_terminal`) share one shape — origin check → accept → `asyncio.wait(FIRST_COMPLETED)` over paired input/output pump tasks → cancel loser → `session.close()` — and the tmux variant treats close as detach, not kill, so the session outlives the socket; `_is_allowed_terminal_origin` is the sole CSRF-style guard on that upgrade and allows a missing Origin header outright. `_serve_project_file` is the only path-traversal guard for downloads (`target.relative_to(base_dir)` must succeed); `download_task_file` feeds it a path resolved via `task.project_name` in preference to raw `task.project`, mirroring the project_name-precedence convention used elsewhere. Endpoints doing directory scans or subprocess calls (`docker inspect`, workflow-run listing, project/account listing) must run inside `run_in_threadpool` — added after synchronous versions blocked the event loop and starved concurrent SSE/WebSocket connections.

- `coderfleet/server/scheduler.py` — Core task queue: resolves account/project, spawns tasks as detached `docker exec` processes, tracks state via `tasks/*.json`, drives conversation/session chaining and workflow execution. Dispatch is snapshot-then-recheck, not lock-based: `schedule_next_tasks` scans a `Task.load_all` snapshot once per 1s tick, but `_start_pending_task` re-reads the task from disk and bails unless it's still `pending`, closing a race where a task is killed between scan and dispatch (regression-tested: `test_start_pending_task_skips_when_cancelled_before_dispatch`). At most one task per `conversation_id` may be in flight at a time — enforced via `busy_conv_ids` ∪ `in_flight_conv_ids` within a scheduling pass plus a hard reject in `ensure_conversation_available` — because native `--resume` session chaining assumes exactly one CLI process per conversation. `depends_on` gates dispatch: pending on any unfinished dependency, cascades to `failed` if a dependency is `None`/`failed`/`killed`, dispatches only once all deps are `done`. Account resolution never silently falls back — mismatched explicit `account_name` vs. a project's bound account raises `ValueError` — and secondary accounts (`project.secondary_accounts`) never enter task dispatch, existing solely to mount extra CLI credentials; the enforced invariant is that no two accounts on a project, primary or secondary, share a `type`. `find_project_for_path` resolves nested projects by longest-prefix match so a child project always wins over its parent workspace root. `_stream_container_log` captures `native_session_id` from only the first log chunk that yields one and persists it immediately to both the task and conversation, so a killed task still leaves a resumable session id. On restart, `reconcile_running_tasks` must check `is_task_process_alive` (a `pgrep`-matched marker string, `coderfleet-task-<id>`, not PID — PIDs aren't stable across `docker exec` reattachment) before trusting a host `.exit` file — a live process always wins and gets reattached rather than treated as exited; this must run before anything else touches `running` tasks on startup. `kill_task` flips status to `killed` before cancelling the asyncio task ("update status first to prevent concurrent writes"), then awaits `bg.cancel()` under `asyncio.shield` with a 3s timeout so the task's own `CancelledError` cleanup still runs. `build_cli_command`'s `( ... )` subshell wrapping is load-bearing: it lets `exec -a` replace only the inner subshell so the outer wrapper can still capture `$?` after exec — don't flatten it. `MAX_PENDING_PER_CONV = 5` is the single shared cap consumed by both the API and the Telegram bridge via `conversation_queue_full` — do not reimplement it locally elsewhere. Usage probing always runs inside the account's own container, never bare from the host — hitting the vendor API sometimes via proxy, sometimes not, risks anti-abuse flags.

- `coderfleet/server/models.py` — Pydantic domain models (Account, Project, Task, Conversation, Board/BoardCard, ImageBuild, Pipeline/WorkflowTemplate/WorkflowRun, Schedule) and their HTTP request/response shapes; single source of truth for record shape across CLI, scheduler, and Web UI. `Task.project`/`project_name` and `Conversation.project`/`project_name` are deliberately duplicated, not redundant: `project` is the host path, `project_name` the config name, and disambiguation code across `scheduler.py` branches on `project_name` truthiness before falling back to path matching — never collapse these. Every `*Response.from_*` classmethod reads newer fields via `getattr(obj, "field", default)` rather than direct access, a deliberate backward-compat guard for records loaded from pre-migration on-disk JSON; new fields need a concrete default and should follow this convention if read in a `from_*` method. Dead fields removed in `0aca8a3` (#32) — `Board.project_name`, `WorkflowRun.template_version`, and the `artifact_sync` workspace-policy value — must not be re-added; they were write-only or unimplemented placeholders. `Project.secondary_accounts` performs no validation itself (the one-account-per-type-per-project rule lives in the CLI/API layer) and is never read by `Task`/`Conversation`, which stay bound to the primary `account` only. `Pipeline` is explicitly marked deprecated (internal execution-engine state only, no user-facing create routes); `WorkflowRun` is the live v2 entity and was added purely additively so legacy `Pipeline`/`WorkflowTemplate` records keep parsing. `TaskHeartbeat` is deliberately minimal (id/status/conversation_id/finished only) for 5-second polling — do not add heavy fields like `prompt`/`images` to it. `TASK_STATUS_LABELS` (added in `b315ea7`) is the single shared map from terminal `TaskStatus` to notification title/broadcast-eligibility, used by both Web Push and Telegram — don't duplicate this set elsewhere.

- `coderfleet/server/settings_schema.py` — Declarative single-source-of-truth registry for every editable `config.conf` key; `GET/PUT /api/config` and the settings UI all derive from `SETTINGS_GROUPS`. `field_for()` matches keys case-insensitively via `.upper()`. `mask_secret()` is the only place secret redaction happens — empty/whitespace input returns `""`, otherwise only the last 4 chars are revealed when `len(value) > 4`; `PUT` treats an empty submitted value for a `secret=True` field as "keep unchanged," never "clear it," so the endpoint depends on `field_for(key).secret` to decide whether to skip the write. `requires_apply` is the sole signal for the UI's "需 apply" badge (network/proxy/image/docker fields are `True`; `system_llm`/`telegram` are live-effect) — locked by `test_apply_flags_split_live_vs_infra`. Field keys must stay space-free since `config.conf` is space-delimited (`test_schema_values_are_space_free_conf_safe`).

- `coderfleet/server/static/js/settings.js` — Pure rendering/submission layer over the `settings_schema` registry fetched via `GET /api/config`; new schema fields render automatically with no hardcoded field list. Secret fields always render as empty password inputs, and `saveSettingsGroup()` omits a secret field from the PUT payload when its input is left blank (`if (f.secret && !v) return;`) — this must stay paired with the backend's "blank secret = keep unchanged" contract in `settings_schema.py`. `refreshTelegramStatus()` only fills the status message if it's currently empty, avoiding a race where it clobbers a fresher `testTelegram()` result. The active-tab choice persists to `localStorage['coderfleet.settings.activeTab']` but is validated against the fixed `SETTINGS_TABS` allowlist before use — a stale/unrecognized stored value falls back to `'preferences'` rather than rendering blank. Saving the `system_llm` group must call `initSystemLlmStatus()` afterward to refresh the chat bubble's translation-availability indicator.

- `coderfleet/server/push_manager.py` — Owns VAPID keypair lifecycle and Web Push subscription storage/delivery; degrades to a fully inert no-op when `pywebpush` isn't installed, so callers must check `.enabled`/`.public_key_b64` first. The VAPID public key must stay in uncompressed EC point → urlsafe-base64 (no padding) form — that's the exact format browsers require for `applicationServerKey`. Corrupt/unreadable `push_keys.json` triggers silent key regeneration rather than raising, which invalidates existing subscriptions (they were signed against the old key). `add_subscription` dedupes by `endpoint`. `send_all` offloads the blocking `pywebpush.webpush()` calls to an executor thread since the library is sync-only; a 404/410 prunes the subscription as expired, but other exceptions are only logged — a transient failure must not wrongly delete a live subscription. `task_push_notifier()` sources titles from the shared `TASK_STATUS_LABELS` (previously a locally hardcoded dict causing status drift, fixed in `b315ea7`) — must not reintroduce a local copy.

- `coderfleet/server/summarize_title.py` — Thin domain-policy wrapper around `SystemLLM.complete()` that generates a session title from the first user message. `_SYSTEM_PROMPT` (title only, ≤16 chars, no quotes/punctuation/preamble) is the entire contract — keep it a single system-prompt string, not app logic, structurally identical to `translate.py`. Empty/whitespace-only input short-circuits to `""` before touching the LLM. Uses the system-level LLM, not a pooled account container, so failures here must never be treated as task failures — the caller (`chat.js` `_autoTitleConversation`) silently swallows errors and keeps its own fallback name.

- `coderfleet/server/static/js/chat.js` — Front-end core for the chat room: conversation list, active-conversation state, inline rename, silent auto-titling. `selectConversation(convId)` must call `rerenderChatProjectList()` synchronously before any awaited network call (fixed in `d6b471e`) — the sidebar highlight previously lagged a full round-trip behind the click. `inlineRenameConversation` must attach `input.addEventListener('click', e => e.stopPropagation())` before the input enters the DOM (fixed in `bec0523`), or a click meant to place the caret bubbles to the row's click handler and fires `selectConversation`, switching away from the item being renamed. `renderConversations`/`_refreshQueuePanel` must check the `_isRenamingConversation`/`_isEditingQueueItem` flags before rerendering (fixed in `40e3e85`) — a rerender mid-edit silently discards the user's in-progress input; both flags must also be cleared on Escape before the rerender fires. `_autoTitleConversation` is fire-and-forget (no `await` at the call site, `.catch` swallowed) and must never block or throw into the send-message path — on any failure it leaves the caller's already-set fallback name untouched rather than overwriting it with something worse.

- `coderfleet/data/Dockerfile` — Single shared image for every account container; every pinned version here is fleet-wide. `ENV LANG=C.UTF-8`/`LC_ALL=C.UTF-8` must stay set (`2e3bdaa`) — without it bash readline mis-echoes multibyte UTF-8 (breaks Chinese input); Ubuntu 24.04 needs no `locale-gen` since C.UTF-8 ships with glibc. Python installs use `--break-system-packages` (Ubuntu 24.04 enforces PEP 668 on the system interpreter). Hermes installs into an isolated venv (`/opt/hermes-venv`) rather than system pip because apt-managed `PyJWT` has no RECORD file and can't be uninstalled by pip if they collide. RTK's installer verifies a SHA-256 checksum before extracting — a supply-chain check; don't swap for an unverified curl-pipe. `USER byclaw` must stay the very last line, after every root-requiring install (apt, playwright system deps) — moving it earlier breaks any subsequent root-only `RUN`.
