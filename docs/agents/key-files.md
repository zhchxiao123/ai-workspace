## Entries

- `coderfleet/server/telegram_bridge.py` — Telegram long-poll bridge: command routing, topic-per-project registration, broadcast, ASR. All state mutations (offset, per-chat sections, topic registry) must go through `_update_state`/`_set_chat_entry` — a synchronous read-modify-write with no `await` inside the mutator, so it's atomic under the event loop; a separate read-then-write reintroduces the race that `_advance_offset` was written to close (long-poll offset writeback must never clobber a `notify_task` mapping persisted while the poll was suspended). `_ensure_topic` concurrent-create resolves by "first registrant in the state file wins" — a thread created after losing the race is dropped, never re-registered. `is_configured()` is true if `token` and EITHER `chat_ids` OR `topic_group_id` is set — do not require both; group membership is its own trust boundary. `poll_timeout` is 25s, not 50s — proxied long-poll tunnels commonly kill idle connections at 30s+, so a 50s window causes a `ReadTimeout` every round; if you touch the poll loop, keep this under ~28s. `_advance_offset` runs unconditionally after each update regardless of handler success — a poison message must not stall the queue. `_hint_topic_permission_once`'s one-time flag is only persisted after the hint send succeeds — a failed send must retry next round, not burn the one-shot. On unknown/invalid references (expired conversation button, reply to an untracked message, a deleted topic thread) the handler must reject/warn explicitly and never silently fall back to "most recent" or a stale default — this class of bug recurred across #46-49 and #51-53 review passes. Broadcast excerpts are extracted by the bridge itself, not reused from the Digest's LLM summary — the Digest summary strips code blocks to `[代码略]` and truncates at 600 chars, which is unacceptable for a code-review broadcast; the bridge's own excerpt keeps code, caps at 3000 chars, with the full message still bounded by Telegram's 4096 hard limit.

- `coderfleet/server/main.py` — FastAPI app defining all REST endpoints and WebSocket terminal handlers; wires the Telegram bridge and usage-polling loops at startup. `create_task` resolves account/project by fixed precedence — `account` param > `project` (mounted-path match) > `type` > first idle account — and must check `scheduler.conversation_queue_full(req.conversation_id)` before calling `scheduler.submit`; `MAX_PENDING_PER_CONV` is imported from `scheduler.py`, never redefined locally, since a prior local recount in main.py drifted out of sync with an equivalent check in `telegram_bridge.py` (fixed in `b315ea7`). `reconcile_tasks_on_startup` requires `telegram_bridge.start_polling()` to run before `scheduler.reconcile_running_tasks()`, so the bridge is wired before any reconciled task can complete and try to notify through it. Both WebSocket terminal handlers (`project_terminal`, `conversation_terminal`) share one shape — origin check → accept → `asyncio.wait(FIRST_COMPLETED)` over paired input/output pump tasks → cancel loser → `session.close()` — and the tmux variant treats close as detach, not kill, so the session outlives the socket; `_is_allowed_terminal_origin` is the sole CSRF-style guard on that upgrade and allows a missing Origin header outright. `_serve_project_file` is the only path-traversal guard for downloads (`target.relative_to(base_dir)` must succeed); `download_task_file` feeds it a path resolved via `task.project_name` in preference to raw `task.project`, mirroring the project_name-precedence convention used elsewhere. Endpoints doing directory scans or subprocess calls (`docker inspect`, workflow-run listing, project/account listing) must run inside `run_in_threadpool` — added after synchronous versions blocked the event loop and starved concurrent SSE/WebSocket connections. Every `sched.updated`/`last_run_at`/`digest.generated_at`/`record.updated` assignment and the `/api/stats/usage` `cutoff` comparison use `now_iso()`/`utc_now()`/`parse_iso()` from `models.py`, not bare `datetime` — `main.py` no longer imports `datetime` at module scope at all (only a local `timedelta` inside `get_usage_stats`); re-adding a bare `datetime.now().isoformat()` anywhere here reintroduces the host/browser-timezone-dependent "刚刚 forever" bug fixed across `models.py`/`scheduler.py`. `stream_logs`'s continuous polling loop buffers cross-iteration bytes via `log_parser.split_complete_lines` before decoding/yielding — same UTF-8-character-corruption class as `scheduler.py`'s host-log poller (see that file's entry); the one-time `skip_bytes`/`tail` initial reads are left as plain single reads since `log_path` (post that fix) never has a partial trailing line to observe at any snapshot.

- `coderfleet/server/scheduler.py` — Core task queue: resolves account/project, spawns tasks as detached `docker exec` processes, tracks state via `tasks/*.json`, drives conversation/session chaining and workflow execution. Dispatch is snapshot-then-recheck, not lock-based: `schedule_next_tasks` scans a `Task.load_all` snapshot once per 1s tick, but `_start_pending_task` re-reads the task from disk and bails unless it's still `pending`, closing a race where a task is killed between scan and dispatch (regression-tested: `test_start_pending_task_skips_when_cancelled_before_dispatch`). At most one task per `conversation_id` may be in flight at a time — enforced via `busy_conv_ids` ∪ `in_flight_conv_ids` within a scheduling pass plus a hard reject in `ensure_conversation_available` — because native `--resume` session chaining assumes exactly one CLI process per conversation. `depends_on` gates dispatch: pending on any unfinished dependency, cascades to `failed` if a dependency is `None`/`failed`/`killed`, dispatches only once all deps are `done`. Account resolution never silently falls back — mismatched explicit `account_name` vs. a project's bound account raises `ValueError` — and secondary accounts (`project.secondary_accounts`) never enter task dispatch, existing solely to mount extra CLI credentials; the enforced invariant is that no two accounts on a project, primary or secondary, share a `type`. `find_project_for_path` resolves nested projects by longest-prefix match so a child project always wins over its parent workspace root. `_stream_container_log` captures `native_session_id` from only the first log chunk that yields one and persists it immediately to both the task and conversation, so a killed task still leaves a resumable session id. It polls `host_log`'s byte size every 0.3s and copies new bytes to `log_path` via `_write_chunk`, buffering in `pending: bytes` across iterations and flushing only through `log_parser.split_complete_lines` — never decode/write a byte range that doesn't end on a `\n`. This isn't optional tidiness: decoding a raw byte-range chunk that happens to end mid-multi-byte-UTF-8-character (routine — task content here is frequently Chinese) replaces that character with U+FFFD garbage on **both** sides of the cut via `errors="replace"`, and no amount of later string concatenation can undo it; if the corruption lands near a JSON structural byte the whole line fails to `JSON.parse` client-side and degrades to raw/garbled display in the Web UI (`renderer.js`'s `_rawLine` fallback) — this is what a real incident looked like after CC's `tool_use_result` payloads grew large enough to make an unlucky mid-character poll tick likely (bigger lines take longer to write, giving more polls a chance to land mid-line). Regression test: `test_stream_container_log_does_not_corrupt_utf8_char_split_across_poll_tick` in `tests/test_runtime.py`, which reproduces the exact `���` corruption via a call-counted fake `asyncio.sleep` (deterministic, not a real-time race) — remove the `split_complete_lines` buffering and this test fails immediately. `pending` must be force-flushed once `is_done` — a final line with no trailing newline would otherwise sit in memory and never reach disk. `main.py`'s `stream_logs` SSE tail independently applies the same `split_complete_lines` buffering to its own continuous-polling loop as defense in depth, even though it reads from `log_path` (which this function now guarantees only ever grows in complete-line increments) rather than `host_log` directly. On restart, `reconcile_running_tasks` must check `is_task_process_alive` (a `pgrep`-matched marker string, `coderfleet-task-<id>`, not PID — PIDs aren't stable across `docker exec` reattachment) before trusting a host `.exit` file — a live process always wins and gets reattached rather than treated as exited; this must run before anything else touches `running` tasks on startup. `kill_task` flips status to `killed` before cancelling the asyncio task ("update status first to prevent concurrent writes"), then awaits `bg.cancel()` under `asyncio.shield` with a 3s timeout so the task's own `CancelledError` cleanup still runs. `build_cli_command`'s `( ... )` subshell wrapping is load-bearing: it lets `exec -a` replace only the inner subshell so the outer wrapper can still capture `$?` after exec — don't flatten it. `MAX_PENDING_PER_CONV = 5` is the single shared cap consumed by both the API and the Telegram bridge via `conversation_queue_full` — do not reimplement it locally elsewhere. Usage probing always runs inside the account's own container, never bare from the host — hitting the vendor API sometimes via proxy, sometimes not, risks anti-abuse flags. Two timestamp regimes coexist here on purpose, do not merge them: (1) audit/display fields (`Conversation.updated`, `WorkflowRun.updated`/`NodeExecution.started_at`/`finished_at`, `Schedule.updated`/`last_run_at`, `ephemeral_expires_at`, `AccountUsage.fetched_at`) are generated via `now_iso()`/`utc_now()` and read back via `parse_iso()` (all from `models.py`) so they're UTC-aware and safe to compare/sort regardless of host timezone — `pending_tasks.sort()` in `schedule_next_tasks` and `list_workflow_runs`'s sort both parse through `parse_iso()` rather than comparing raw strings, since raw-string comparison silently breaks across the naive→aware migration boundary; (2) `_compute_next_run_at`/`_check_and_trigger_schedules`/`_validate_future_execute_at`/`schedule_next_tasks`'s `execute_at` check, and `_check_auto_digest`'s 23:30 gate, intentionally keep using bare naive `datetime.now()` — schedule/cron wall-clock math (`time_of_day="14:30"`) is defined in the scheduler host's local time by design, and converting it to UTC would fire schedules at the wrong wall-clock hour, not just cosmetically mis-format a display string.

- `coderfleet/server/models.py` — Pydantic domain models (Account, Project, Task, Conversation, Board/BoardCard, ImageBuild, Pipeline/WorkflowTemplate/WorkflowRun, Schedule) and their HTTP request/response shapes; single source of truth for record shape across CLI, scheduler, and Web UI. `Task.project`/`project_name` and `Conversation.project`/`project_name` are deliberately duplicated, not redundant: `project` is the host path, `project_name` the config name, and disambiguation code across `scheduler.py` branches on `project_name` truthiness before falling back to path matching — never collapse these. Every `*Response.from_*` classmethod reads newer fields via `getattr(obj, "field", default)` rather than direct access, a deliberate backward-compat guard for records loaded from pre-migration on-disk JSON; new fields need a concrete default and should follow this convention if read in a `from_*` method. Dead fields removed in `0aca8a3` (#32) — `Board.project_name`, `WorkflowRun.template_version`, and the `artifact_sync` workspace-policy value — must not be re-added; they were write-only or unimplemented placeholders. `Project.secondary_accounts` performs no validation itself (the one-account-per-type-per-project rule lives in the CLI/API layer) and is never read by `Task`/`Conversation`, which stay bound to the primary `account` only. `Pipeline` is explicitly marked deprecated (internal execution-engine state only, no user-facing create routes); `WorkflowRun` is the live v2 entity and was added purely additively so legacy `Pipeline`/`WorkflowTemplate` records keep parsing. `TaskHeartbeat` is deliberately minimal (id/status/conversation_id/finished only) for 5-second polling — do not add heavy fields like `prompt`/`images` to it. `TASK_STATUS_LABELS` (added in `b315ea7`) is the single shared map from terminal `TaskStatus` to notification title/broadcast-eligibility, used by both Web Push and Telegram — don't duplicate this set elsewhere. `now_iso()`/`utc_now()`/`parse_iso()` are the single source for every `created`/`updated`/`finished`/`started_at`/`finished_at` field on every model here — never call bare `datetime.now().isoformat()` again. Root cause: a naive (tz-less) timestamp gets parsed by the browser as local-browser-time, so any skew between the host running `coderfleet server` and the browser's clock/timezone could push it into the apparent future, and the frontend's `fmtTime()` had no floor on negative diffs — it stuck on "刚刚" forever instead of ever ticking over. `now_iso()` emits UTC-aware ISO strings (`+00:00` suffix) so display no longer depends on host/browser timezone agreement; `parse_iso()` is the required read-side counterpart — it transparently upgrades pre-migration naive strings already on disk (assumes host-local, matching their original semantics) so aware/naive values never get compared directly (`TypeError`) or sorted as raw strings across the migration boundary.

- `coderfleet/server/settings_schema.py` — Declarative single-source-of-truth registry for every editable `config.conf` key; `GET/PUT /api/config` and the settings UI all derive from `SETTINGS_GROUPS`. `field_for()` matches keys case-insensitively via `.upper()`. `mask_secret()` is the only place secret redaction happens — empty/whitespace input returns `""`, otherwise only the last 4 chars are revealed when `len(value) > 4`; `PUT` treats an empty submitted value for a `secret=True` field as "keep unchanged," never "clear it," so the endpoint depends on `field_for(key).secret` to decide whether to skip the write. `requires_apply` is the sole signal for the UI's "需 apply" badge (network/proxy/image/docker fields are `True`; `system_llm`/`telegram` are live-effect) — locked by `test_apply_flags_split_live_vs_infra`. Field keys must stay space-free since `config.conf` is space-delimited (`test_schema_values_are_space_free_conf_safe`).

- `coderfleet/server/static/js/settings.js` — Pure rendering/submission layer over the `settings_schema` registry fetched via `GET /api/config`; new schema fields render automatically with no hardcoded field list. Secret fields always render as empty password inputs, and `saveSettingsGroup()` omits a secret field from the PUT payload when its input is left blank (`if (f.secret && !v) return;`) — this must stay paired with the backend's "blank secret = keep unchanged" contract in `settings_schema.py`. `refreshTelegramStatus()` only fills the status message if it's currently empty, avoiding a race where it clobbers a fresher `testTelegram()` result. The active-tab choice persists to `localStorage['coderfleet.settings.activeTab']` but is validated against the fixed `SETTINGS_TABS` allowlist before use — a stale/unrecognized stored value falls back to `'preferences'` rather than rendering blank. Saving the `system_llm` group must call `initSystemLlmStatus()` afterward to refresh the chat bubble's translation-availability indicator.

- `coderfleet/server/push_manager.py` — Owns VAPID keypair lifecycle and Web Push subscription storage/delivery; degrades to a fully inert no-op when `pywebpush` isn't installed, so callers must check `.enabled`/`.public_key_b64` first. The VAPID public key must stay in uncompressed EC point → urlsafe-base64 (no padding) form — that's the exact format browsers require for `applicationServerKey`. Corrupt/unreadable `push_keys.json` triggers silent key regeneration rather than raising, which invalidates existing subscriptions (they were signed against the old key). `add_subscription` dedupes by `endpoint`. `send_all` offloads the blocking `pywebpush.webpush()` calls to an executor thread since the library is sync-only; a 404/410 prunes the subscription as expired, but other exceptions are only logged — a transient failure must not wrongly delete a live subscription. `task_push_notifier()` sources titles from the shared `TASK_STATUS_LABELS` (previously a locally hardcoded dict causing status drift, fixed in `b315ea7`) — must not reintroduce a local copy.

- `coderfleet/server/summarize_title.py` — Thin domain-policy wrapper around `SystemLLM.complete()` that generates a session title from the first user message. `_SYSTEM_PROMPT` (title only, ≤16 chars, no quotes/punctuation/preamble) is the entire contract — keep it a single system-prompt string, not app logic, structurally identical to `translate.py`. Empty/whitespace-only input short-circuits to `""` before touching the LLM. Uses the system-level LLM, not a pooled account container, so failures here must never be treated as task failures — the caller (`chat.js` `_autoTitleConversation`) silently swallows errors and keeps its own fallback name.

- `coderfleet/server/static/js/chat.js` — Front-end core for the chat room: conversation list, active-conversation state, inline rename, silent auto-titling. `selectConversation(convId)` must call `rerenderChatProjectList()` synchronously before any awaited network call (fixed in `d6b471e`) — the sidebar highlight previously lagged a full round-trip behind the click. `inlineRenameConversation` must attach `input.addEventListener('click', e => e.stopPropagation())` before the input enters the DOM (fixed in `bec0523`), or a click meant to place the caret bubbles to the row's click handler and fires `selectConversation`, switching away from the item being renamed. `renderConversations`/`_refreshQueuePanel` must check the `_isRenamingConversation`/`_isEditingQueueItem` flags before rerendering (fixed in `40e3e85`) — a rerender mid-edit silently discards the user's in-progress input; both flags must also be cleared on Escape before the rerender fires. `_autoTitleConversation` is fire-and-forget (no `await` at the call site, `.catch` swallowed) and must never block or throw into the send-message path — on any failure it leaves the caller's already-set fallback name untouched rather than overwriting it with something worse. `_fetchTaskLogCached` only writes to `_finishedLogCache`/IndexedDB (`log-cache.js`) when `_looksLikeCompleteTaskLog(text)` passes (a line of `======` followed by `finished:`/`usage status:` — the same marker `renderer.js`'s `render()` state machine looks for) — `scheduler.py` flips a task's status to `done`/`failed`/`killed` *before* `_append_usage_status`/`_append_log_footer` finish writing that trailing marker (there's a `docker exec` in between that can take real wall-clock time), so a fetch that lands in that window used to get permanently cached as "the finished log" with some tool_use blocks never resolved (stuck showing `⏳` forever, even across refreshes, since IndexedDB persists it) — this was a real reported bug, not theoretical. `_selfHealStuckToolStatus`, called after every eager task render in `renderChatWorkspace`, is the *retroactive* half of the fix: for any non-running task whose rendered DOM still has a `.tool-status` reading `⏳`, it purges that task's cache entry (`logCacheDelete`, `log-cache.js`) and force-refetches/re-renders once — without this, everyone who already had a bad entry cached before the fix landed would stay stuck until that IndexedDB row aged out via `LOG_CACHE_MAX_ENTRIES` eviction. Both are gated on `_looksLikeCompleteTaskLog`, so a task whose log genuinely isn't finished yet (server-side) is left alone rather than looping.

- `coderfleet/server/static/js/workflows.js` — Front-end for the `Workflow`/`WorkflowRun` DAG surface (runs tab + template/Drawflow editor); per `CONTEXT.md`, node status must be read from `WorkflowRun.node_executions[].state` (the eight-state node-status machine), never inferred from `task.status` or a legacy `node_runs` field — `_dagNodeState`/`_dagStateMeta`/`WF_NODE_STATE_META` are the sole translation layer, and `task.status` is only a fallback for pre-`node_executions` legacy runs (fixed in `7976cb3`, closes #10/#13/#14). `loadWorkflows()` polls every 5s via `app.js`'s global interval whenever the runs tab is active; the poll must go through `_patchDagIfRendered`, not `renderDag` directly — it diffs node count against the current DOM and only falls back to a full rerender when node count changed, otherwise patching per-node class/flags/duration in place via `_patchDagNode` so `workflowSelectedTaskId`'s selected-node highlight and the open detail panel survive the poll. `loadTemplates()` checks `templateDirty` before touching the Drawflow canvas (`if (templateDirty) return;`) — same in-progress-edit-vs-rerender-discard class as `chat.js`'s `_isRenamingConversation` guard, gating a canvas rebuild instead of a list rerender. `_loadTemplateToCanvas`'s double-`requestAnimationFrame` connection-restore callback is guarded by `importVersion !== drawflowImportVersion` — without it, opening a second template before the first one's rAF pair fires would restore connections onto the already-replaced canvas. `dfEditor`'s `connectionCreated`/`connectionRemoved` handlers check `suppressTemplateDirty` before calling `markTemplateDirty()`, since the programmatic `addConnection` calls made while restoring connections would otherwise mark a freshly-loaded, unedited template as dirty. `saveTemplate` must run its payload through `_dedupeTemplateNodeIds` (never save `_getTemplateFromCanvas()` directly) — duplicate/renamed `node_id`s from a Drawflow copy-paste-style import otherwise silently corrupt `depends_on` edges.

- `coderfleet/account_type_registry.py` — Single registration point for CLI account types (`claude`/`codex`/`opencode`/`hermes`/`grok`/`kimi`/`pi`); `compose.py`, `login_cmd.py`, `scheduler.py`'s command-building, `config_cmds.py`, `server/models.py`'s `AccountType` enum, and the Web UI account cards all derive account-type behavior from `ACCOUNT_TYPES` generically — adding a type means adding one `AccountTypeSpec` entry here, never a new `if acc_type == "..."` branch in those files. `AccountType` is derived from `ACCOUNT_TYPES.keys()` at import time — never hand-declare a parallel `AccountType(str, Enum)`, it would drift the moment a type is added/removed here (same class of duplication `b315ea7` fixed for `TASK_STATUS_LABELS`/`MAX_PENDING_PER_CONV`). `env_auth_type_ids()`/`valid_type_ids()` are the only sanctioned way to enumerate types outside this module. Each `_build_<type>`/`_extract_<type>` pair must stay a pure function (no I/O) — that's what makes them directly unit-testable without Docker (`tests/test_account_type_registry.py`). `pi`'s `_build_pi` maps CoderFleet's `auto` flag to pi's `--approve`/`--no-approve` (project-trust for loading `.pi/` config), not a real permission gate — pi has no tool-confirmation system by design, its own container is the safety boundary it expects, so `auto` does not toggle "restricted vs. unrestricted" tool execution for pi the way it does for `claude`/`codex`. `_build_pi` attaches `images` as `@path` positional args (pi's real attachment mechanism, per its own docs — for images this sends actual multimodal bytes, not just a path) — do NOT "fix" this to match `claude`/`grok`/`kimi`'s convention of folding image paths into the prompt text as a `[Attached images: ...]` hint; that convention exists only because those CLIs lack a native attachment flag, pi has one and it's strictly better. **This registry is NOT the only place a new type needs wiring** — `server/log_parser.py` (task-output/token-usage extraction) and `server/static/js/renderer.js` (Web UI log rendering) both hardcode a per-type event vocabulary and do NOT derive from `ACCOUNT_TYPES`; adding a type here without also adding a branch in both of those leaves the new type's tasks logging correctly but rendering as raw/empty in the Web UI and yielding no `{{steps.X.outputs.text}}`/usage stats (this exact gap shipped for `pi` and had to be patched in as a follow-up — see those files' own entries).

- `coderfleet/server/log_parser.py` — Parses a completed task's raw log into `TaskOutputData` (final text + token/cost usage), consumed by `GET /api/tasks/{id}/output` (workflow `{{steps.X.outputs.text}}`), `scheduler.py`'s `_extract_and_save_token_usage`, and Digest AI-summary capture. `parse_log()` dispatches on `acc_type` — NOT derived from `account_type_registry.py`'s `ACCOUNT_TYPES`, so every account type needs its own `_parse_<type>_line` branch added here explicitly (missed for `pi` on first landing; see `account_type_registry.py`'s entry). `hermes` is deliberately absent from the JSONL dispatch list — it's plain text, not JSONL, and relies entirely on `_parse_text_fallback`. `_parse_codex_line`/`_parse_opencode_line` must stay in sync with the exact event shape `renderer.js`'s `_codexItemCompleted`/`_opencodeText`/`_opencodeStepFinish` parse (both files independently hardcode the same vocabulary — see this file's own top-level "don't duplicate" invariant) — this drifted once already: both parsers only matched an older flat/top-level event shape (`type:"message"` + top-level `content`/`usage`) while the CLIs actually invoked via `codex exec --json`/opencode's real stream had moved on to `item.completed`'s `item.type==="agent_message"` text + `turn.completed.usage` (codex, cumulative-not-delta — overwrite on each occurrence, don't sum) and `part`-nested `part.text`/`part.tokens` (opencode) respectively; every codex/opencode task's `result.text` was silently falling back to a raw JSONL dump via `_parse_text_fallback` and token/cost usage read as zero, with zero test coverage catching it (fixed together with the matching `renderer.js` gaps; regression tests in `tests/test_log_parser.py`). Legacy flat-shape handling was kept alongside the fix (not removed) as a defensive fallback for any older-format log still on disk. `_parse_pi_line` only reads `message_end` (never `agent_end`, which re-lists the same messages) to avoid double-counting text/usage across duplicate event coverage of the same turn. Also hosts `split_complete_lines(buf: bytes) -> (complete, pending)`, a tiny line-boundary-safe helper shared by every place that tails a growing log file in byte chunks — `scheduler.py`'s `_stream_container_log` (host_log → log_path) and `main.py`'s `stream_logs` SSE tail both import it rather than reimplementing the same "don't decode/emit a byte range that doesn't end on a real newline" check locally; see `scheduler.py`'s entry for why (mid-UTF-8-character corruption, not just cosmetic line-splitting).

- `coderfleet/server/static/js/renderer.js` — `ChatLogRenderer`, the Web UI's task/conversation log viewer. Per-type event vocabulary is hardcoded and, like `log_parser.py`, does NOT derive from `account_type_registry.py` — a new account type needs its own `case`s in `_event()`'s switch (or a dedicated `_<type>Line()` parser routed from `_processLine()`, the pattern used for `hermes`/`grok`/`kimi` because their formats aren't single-line-JSON-per-event). Anything reaching the `default` case renders as a raw `JSON.stringify` dump — that's the visible symptom of a type missing its branch here (shipped for `pi` on first landing). `_footerRendered` is a first-write-wins latch shared across every type's own footer call (`_claudeResult`/`_codexEnd`/`_opencodeStepFinish`/`_grokEnd`/`_piAgentEnd`) and the wrapper-appended `finished:` line in `push()`/`render()` — whichever fires first is final, so a type's own end-of-turn handler must only call `_renderFooter('done')` when it has a genuinely authoritative success signal from its own JSON (`pi`'s `_piAgentEnd` checks `willRetry` and skips rendering if true, leaving the footer to a later authoritative event); a premature or wrong self-reported 'done' cannot be corrected by the wrapper's real exit-code-based footer arriving afterward. `_fillTool` caps tool-result text at `TOOL_OUTPUT_TRUNCATE_LEN` (8000 chars) via `_setToolOutputText`, appending a "show full output" button instead of writing the whole string into `textContent` — some real logs carry a single Bash/Read output in the hundreds-of-KB range, and building that much DOM text for every tool card (mostly sitting inside the collapsed "任务执行过程" section) was the main cause of slow/janky history loading, especially on mobile CPUs. This is shared across every account type since they all funnel through `_fillTool`; don't reintroduce an unbounded `textContent =` assignment for tool output. `_toolUse` special-cases `name === 'Edit'` with `old_string`/`new_string` present: it routes through `renderInlineDiff` (utils.js, LCS line diff, falls back to a straight del-all/add-all split above a 200 000-line-product size guard) instead of the generic `formatToolInput` JSON/text preview — any other tool with old/new-string-shaped input still gets the generic preview, this is not a general diff feature. Auto-expand no longer relies solely on the output-size heuristic: `ChatLogRenderer.ALWAYS_EXPAND_TOOLS` (`Edit`/`Write`/`TodoWrite`/`Task`) always expands regardless of output size, and `Read` additionally auto-expands when its result carried an image (see below); everything else still falls back to the old ≤6-lines/≤400-chars check. `AskUserQuestion` bypasses `_toolUse`/`_fillTool`'s generic body entirely — `_toolUseAskUserQuestion`/`_fillAskUserAnswers` build a dedicated Q&A card from `normalizeAskUserQuestions(input)` (utils.js, tolerant of a stringified/singular/malformed `questions` field) and best-effort-match the `tool_result` text against each question (JSON object keyed by question text, or `{answers: {...}}`); anything that doesn't parse/match renders as one freeform "✎ reply" line for the whole card instead of forcing it into a Q&A row — don't add new logic here assuming `tool_result` is always structured JSON, CC may return unparseable text. `_claudeUser` splits each `tool_result`'s content array into text blocks and `type: 'image'` blocks (previously the `.map(c => c.text || '')` join silently turned image blocks into `''`, so a `Read` on an image file rendered as blank output) — images are passed as a 4th `_fillTool(id, text, isError, images)` arg and rendered via `_setToolOutputImages` (`<img src="data:...">`, click-to-open-in-new-tab) instead of `_setToolOutputText`; only the Claude code path extracts images today, Codex/OpenCode/Pi/Kimi tool results are still assumed text-only. `Read` tool output additionally runs through `stripReadLineNumbers` (utils.js) before display/auto-expand sizing — Claude Code's `Read` always prefixes each line with a `cat -n`-style `␣␣␣1\t` marker that has no display value once stripped from the underlying file. Sub-agent transcripts (spawned via a `Task`/`Agent` tool_use) are threaded purely client-side off CC's own `parent_tool_use_id` field, which already arrives on the raw JSONL unmodified — no backend change needed. `_toolUse` creates a lazily-revealed nested `ChatLogRenderer` instance per `Task`/`Agent` tool_use (stored in `this.subagentRenderers[toolUseId]`, container starts `display:none` until the first matching event arrives, since not every `Task` call actually forks a sub-conversation); `_event()` intercepts any event carrying `d.parent_tool_use_id` before its own switch and forwards it verbatim to the matching nested renderer's own `_event()` instead of the main timeline — this is recursive by construction (a nested renderer can itself spawn further-nested renderers) and reuses every rendering path (bubbles/tool cards/diff/AskUserQuestion/images) with zero duplication. `render()` and both `push()` reset blocks must clear `this.subagentRenderers = {}` alongside `this.toolMap` — a stale entry there would silently reroute a new run's top-level events into a torn-down nested renderer instead of the main timeline. The trailing `chat-file-card` "EDIT/CREATE path" badge `_fillTool` appends after a successful tool call is now `NotebookEdit`-only — `Write`/`Edit` already show `file_path` in the tool card's own header (`formatToolSummary` has explicit cases for both) and Edit additionally shows the full diff body, so the badge was pure duplication for those two; `NotebookEdit` has no `formatToolSummary`/`formatToolInput` case (falls through to raw JSON preview) so it still needs the badge as its only clean path display — its real path field is `notebook_path` (not `file_path`/`path`; the badge silently never fired before this was added, since it read the wrong field). `TodoWrite` bypasses `_toolUse`/`_fillTool` entirely via `_toolUseTodoWrite` (mirrors the `AskUserQuestion` pattern): the card is fully rendered from `tool_use.input.todos` at creation time (header pill showing current in-progress `activeForm` or "全部完成"/"待办事项" + `completed/total` count, per-row checkbox/strikethrough/arrow-highlight by `status`) since the `tool_result` is just a content-free confirmation string — `toolMap[id].isTodoWrite` short-circuits `_fillTool` to a no-op return before it touches `outputEl`/`exitEl` (both intentionally `null` for this tool). `_setToolOutputText` now runs all tool output through `ansiToHtml` (utils.js) before display — it parses ANSI SGR color/style codes into `<span style="...">` and strips non-SGR CSI sequences (cursor movement etc.) and bare `\r`; the fast path (`indexOf('\x1b') === -1`) makes this a no-op for the common case, so it's applied unconditionally rather than gated per tool name. `Monitor` (CC 2.1+ background command) tool_use renders through the ordinary generic tool card (readable summary/input via `formatToolSummary`/`formatToolInput`'s dedicated cases, using `timeout_ms` not `timeout`) — its start/end lifecycle is separately signaled via `system` events with `subtype: 'task_started'|'task_notification'` (not a normal `tool_result`), tracked in `this.activeMonitorTasks` (`task_id → tool_use_id`) and handled in `_claudeSys`; this is intentionally a light "flip the status glyph" subset, not lobehub's full cross-turn signal-callback attribution (grouping later turns the background task wakes as "belonging" to it) — that needs a real stateful turn-attribution machine disproportionate to a JSONL-to-DOM renderer, so it's out of scope until there's a concrete need. `Skill` tool output renders via `renderMd` (`.tool-output-md` class resets the monospace/pre-wrap styling `.tool-output` normally forces) instead of `_setToolOutputText`, since Skill output is prose/markdown, not raw command output — no truncation guard on this path (unlike `_setToolOutputText`'s 8000-char cap), acceptable because Skill output is short instructional text in practice, not a candidate for the hundreds-of-KB blobs that guard exists for. `ExitWorktree` gets a red `tool-risk-badge` in its card header only when `input.action === 'remove' && input.discard_changes === true` — the one genuinely destructive combination (removes the worktree AND discards uncommitted changes); `action: 'keep'` or a remove without discard gets no badge. Verified against two real production logs (`.coderfleet-tasks`-style raw CC stream-json, no CoderFleet header) with zero `.chat-raw-line` fallbacks and zero JS errors at ~330KB/~1.85MB. `rate_limit_event` (a top-level type, not nested under `system`) is handled by `_claudeRateLimit` and is intentionally silent when `rate_limit_info.status === 'allowed'` (the overwhelming common case — every request carries one) and only pills a warning otherwise; before this it fell to the `_event()` default case and rendered as a raw JSON dump on every single request. `TOOL_ICONS`/`formatToolSummary` also cover CC's newer agent/orchestration tool set (`TaskCreate`/`TaskUpdate`/`TaskGet`/`TaskList`/`TaskOutput`/`TaskStop`/`CronCreate`/`CronDelete`/`CronList`/`DesignSync`/`PushNotification`/`RemoteTrigger`/`ReportFindings`/`ScheduleWakeup`/`SendMessage`/`ToolSearch`/`Workflow`) — icons for all of them, but custom summary formatting only for `TaskCreate`/`TaskUpdate`/`ReportFindings`/`ScheduleWakeup`, the ones whose input schema is actually confirmed (real log data or this project's own tool definitions); the rest deliberately fall through to the generic JSON-preview `default` case rather than guessing a field name that might not exist and rendering a misleading blank summary. `TaskUpdate`/`TaskList` bypass `_toolUse`/`_fillTool` (same pattern as `TodoWrite`/`AskUserQuestion`) via `_toolUseTaskUpdate`/`_toolUseTaskList` — this is a session-wide accumulator (`this.taskBoard`, a `Map<taskIdString, {subject,status,activeForm}>`), not a per-call snapshot (mirrors lobehub's `synthesizeTaskPluginState` accumulator design, ported from a pasted analysis of `packages/heterogeneous-agents/src/adapters/claudeCode.ts` — no `docs/research/` write-up for this one). `TaskCreate` deliberately has no aggregate-board rendering of its own (stays on the generic tool-card path, lobehub's own stated reasoning is that a single-task add showing the whole N/M board is "noise without info"); `_fillTool` special-cases only `e.name === 'TaskCreate' && ok` to regex-parse `Task #(\d+) created successfully` out of its `tool_result` text (the numeric id doesn't exist anywhere in `tool_use.input`, CC assigns it) and register the entry with `status:'pending'`, without an early return (TaskCreate's own output line still renders normally). `TaskUpdate` applies `input.status === 'deleted'` as a `Map.delete`, not a strikethrough row. Cross-checked against lobehub's own `codex.ts`/`opencode.ts` adapters (`packages/heterogeneous-agents/src/adapters/`, canary branch) to find rendering gaps: Codex's `todo_list` item (its plan tool, equivalent to `TodoWrite`) now renders via `_codexTodoList`, which reuses `_toolUseTodoWrite`'s card verbatim for creation but — unlike Claude's `TodoWrite`, which gets a fresh `tool_use.id` per call — Codex reuses the same `item.id` across `item.started`→`item.updated` (zero or more, live progress)→`item.completed`, so subsequent sightings go through `_updateTodoWriteBody`, an in-place `querySelector('.todo-header'/'.todo-list').innerHTML` rewrite rather than a new card; Codex's `{completed: bool}` per-entry shape (no three-state status) is synthesized into `TodoWrite`'s `{content,status,activeForm}` shape the same way lobehub's own `synthesizeTodoListPluginState` does — first incomplete item is `in_progress`, the rest are `pending`. `mcp_tool_call`/`web_search`/`collab_tool_call` (Codex's own MCP-tool, web-search, and spawn_agent/wait sub-agent items) previously had no branch in `_codexItemStarted`/`_codexItemCompleted` at all and were silently dropped (not even a raw-JSON fallback, since the if/else-if chain there has no final `else`) — they now route through the ordinary generic `_toolUse`/`_fillTool` card path via `_isCodexGenericToolItem`, with `_codexMcpResultText` unwrapping the `{Ok:...}/{Err:...}/{ok:...}` result envelope (falling back to unwrapping `item.result` when `item.error` is absent, not just when present — MCP failures report the error either way) and `_codexCollabResultText` summarizing `spawn_agent`/`wait` the same way lobehub's `summarizeCollabToolCall` does. The shared `case 'reasoning'` handler now tries `d.part?.text` before Codex's flat `d.text`/`d.thinking` — OpenCode's reasoning content arrives `part`-wrapped exactly like its `text` events do, and previously resolved to `''`, silently swallowed by `_thinking`'s own empty-string guard. **The task board itself is a single sticky DOM node the whole render/push lifetime, mutated in place — not one card appended per event.** Originally each `TaskUpdate`/`TaskList` call appended a full new board card, so a session with 8 tasks and a dozen updates rendered the same ~8-row list a dozen times down the timeline; this was rebuilt (per product-design discussion, not a lobehub feature) around `_ensureTaskBoardEl()`/`_updateTaskBoardEl()`: the board element (`this.taskBoardEl` + cached `taskBoardIconEl`/`taskBoardLabelEl`/`taskBoardCountEl`/`taskBoardListEl` refs) is created once on the first `TaskCreate`/`TaskUpdate`/`TaskList` event and every subsequent one just rewrites its `textContent`/`innerHTML` in place; each individual `TaskUpdate`/`TaskList` event instead leaves a lightweight one-line `_pill()` marker at its actual chronological position in the timeline, so the narrative ("已开始: X", "已完成: X") is preserved without repeating the whole board. The board is deliberately appended directly to `this.inner` rather than through `_appendNode` — going through `_appendNode` while `foldProcess` is active would let it get folded into the collapsed "任务执行过程" wrapper (`display:none`), which defeats the entire point of a panel that must always stay visible. CSS: `.task-board-sticky` (`position: sticky; top: 8px`) makes it pin to the top of whichever scrolling ancestor contains it — verified against the real desktop chat layout (`#chat-viewport { overflow-y: auto }` → `#chat-content` → `.chat-log`, in `chat.js`); in contexts where no scrolling ancestor exists (a bare log-modal container, say) `sticky` degrades harmlessly to normal in-flow positioning, so this is safe to reuse across `chat.js`/`log.js`/`workflows.js`'s different container structures without per-context testing. `_renderTaskRowHtml` (single-row renderer) is shared between `TodoWrite` and the task board — same visual language, no new row-level CSS was needed, only the sticky-container chrome.

- `coderfleet/data/Dockerfile` — Single shared image for every account container; every pinned version here is fleet-wide. `ENV LANG=C.UTF-8`/`LC_ALL=C.UTF-8` must stay set (`2e3bdaa`) — without it bash readline mis-echoes multibyte UTF-8 (breaks Chinese input); Ubuntu 24.04 needs no `locale-gen` since C.UTF-8 ships with glibc. Python installs use `--break-system-packages` (Ubuntu 24.04 enforces PEP 668 on the system interpreter). Hermes installs into an isolated venv (`/opt/hermes-venv`) rather than system pip because apt-managed `PyJWT` has no RECORD file and can't be uninstalled by pip if they collide. RTK's installer verifies a SHA-256 checksum before extracting — a supply-chain check; don't swap for an unverified curl-pipe. `USER byclaw` must stay the very last line, after every root-requiring install (apt, playwright system deps) — moving it earlier breaks any subsequent root-only `RUN`. `npm install -g npm@<pinned>` must stay pinned to a specific version below npm/cli's `optionalDependencies`-skipping regression window (`>=11.5.0`, npm/cli #8464/#8628) — floating it back to `npm@latest` silently breaks any npm-installed CLI whose native binary ships as an optional dependency (bit `claude` this way: exits 0, binary just isn't there). Any edit to an *earlier* layer (e.g. the Node.js version line) invalidates Docker's build cache for every layer after it, including this one — an otherwise-unrelated Node bump can resurface this class of bug purely by forcing a fresh `npm@latest`-equivalent resolution; re-verify all npm-installed CLIs (`claude`/`codex`/`opencode`) after touching anything above this line.
