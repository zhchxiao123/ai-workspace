## Entries

Continuation addendum for the load-bearing files below:

- `coderfleet/server/auth.py`: `/api/integrations/github/webhook` and
  `/api/continuations/hooks/*` bypass the operator API key only because they
  authenticate with a GitHub HMAC signature or a one-time high-entropy token.
- `coderfleet/server/main.py`: webhook routes validate and normalize input, then
  call `Scheduler.signal_*`; they never create a Task directly. GitHub matching
  uses repository + PR number + head SHA.
- `coderfleet/server/mcp_bridge.py`: `schedule_continuation` persists a future
  Conversation turn and returns immediately; Claude's MCP tool-use id is its
  retry idempotency key.
- `coderfleet/server/scheduler.py`: timer and webhook Adapters converge on
  `fire_continuation`, which deduplicates Task creation by
  `Task.continuation_id` and resumes through the latest Conversation session.
  Failed executions also converge on `_maybe_auto_retry`, configured by
  `TASK_AUTO_RETRY` (default on), `TASK_AUTO_RETRY_MAX`, and
  `TASK_AUTO_RETRY_DELAY_SECONDS`. It only retries a narrow set of transient
  502/503/504/network failures when the log contains no known tool-side-effect
  event, uses exponential backoff, and records
  `retry_of`/`retry_count`/`retry_task_id`. Manual and automatic retry both use
  `clone_task_for_retry` so their cloned task fields cannot drift.
- `coderfleet/server/models.py`: `Continuation` is an internal Conversation
  trigger record, not another execution atom; Task remains the only executor.
- `coderfleet/continuation_cmds.py`: `coderfleet continuation list/add/cancel/trigger`
  — the CLI counterpart to the Continuation REST endpoints, kept alongside them
  per the CLI/Web-UI equal-capability rule rather than shipping Web-only. Pure
  passthrough: it does no validation of its own (e.g. the 10..2592000s
  `--after` range) and trusts the server's `/api/continuations*` responses for
  every error message via `_http_error_detail`; do not duplicate server-side
  checks here.
- `coderfleet/account_type_registry.py`: every Claude task loads the same
  CoderFleet MCP server. `_claude_mcp_bridge_arg(allow_ask_user=...)` varies
  only tool permissions: normal mode pre-approves AskUserQuestion and
  Continuation; auto mode pre-approves Continuation and explicitly disallows
  AskUserQuestion. Never gate the whole MCP config on `auto`.

- `coderfleet/server/telegram_bridge.py` — Telegram long-poll bridge: command routing, topic-per-project registration, broadcast, ASR. All state mutations (offset, per-chat sections, topic registry) must go through `_update_state`/`_set_chat_entry` — a synchronous read-modify-write with no `await` inside the mutator, so it's atomic under the event loop; a separate read-then-write reintroduces the race that `_advance_offset` was written to close (long-poll offset writeback must never clobber a `notify_task` mapping persisted while the poll was suspended). `_ensure_topic` concurrent-create resolves by "first registrant in the state file wins" — a thread created after losing the race is dropped, never re-registered. `is_configured()` is true if `token` and EITHER `chat_ids` OR `topic_group_id` is set — do not require both; group membership is its own trust boundary. `poll_timeout` is 25s, not 50s — proxied long-poll tunnels commonly kill idle connections at 30s+, so a 50s window causes a `ReadTimeout` every round; if you touch the poll loop, keep this under ~28s. `_advance_offset` runs unconditionally after each update regardless of handler success — a poison message must not stall the queue. `_hint_topic_permission_once`'s one-time flag is only persisted after the hint send succeeds — a failed send must retry next round, not burn the one-shot. On unknown/invalid references (expired conversation button, reply to an untracked message, a deleted topic thread) the handler must reject/warn explicitly and never silently fall back to "most recent" or a stale default — this class of bug recurred across #46-49 and #51-53 review passes. Broadcast excerpts are extracted by the bridge itself, not reused from the Digest's LLM summary — the Digest summary strips code blocks to `[代码略]` and truncates at 600 chars, which is unacceptable for a code-review broadcast; the bridge's own excerpt keeps code, caps at 3000 chars, with the full message still bounded by Telegram's 4096 hard limit.

- `coderfleet/server/auth.py` — `AuthMiddleware`, the API-key gate wrapping the entire app (`main.py`'s `app.add_middleware(AuthMiddleware, ...)`, applied to every request unless the path is in `_EXEMPT_PATHS`/`_EXEMPT_PREFIXES`). Real incident (issue #69 Slice 2, found against an actual running deployment, not caught by `tests/test_mcp_bridge.py`'s existing coverage): the Intervention MCP bridge mounted at `/mcp` was silently 401ing every request from Claude's own MCP client, because a newly-mounted sub-app is just as subject to this middleware as any hand-written route, and Claude has no way to know — and shouldn't be given — the app's own API key (a much broader-scoped secret than the one narrow capability `/mcp` exposes; pushing it into every project container's environment as a workaround would let any container impersonate the operator against the *entire* API, a strictly worse exposure than the problem it'd solve). `/mcp/` is now in `_EXEMPT_PREFIXES` alongside `/static/` — it has its own narrower identification scheme (the task-id header, see `mcp_bridge.py`'s entry) instead. The gap existed because `tests/test_mcp_bridge.py`'s other tests mount the MCP server onto a bare `FastAPI()` with no `AuthMiddleware` at all, so they never exercised this interaction; `test_auth_middleware_exempts_mcp_but_still_protects_everything_else` closes that specific hole by mirroring `main.py`'s real construction order (middleware wraps the mount) with a live, non-empty key, and asserts both that `/mcp` gets through *and* that an unrelated path still doesn't — any future sub-app mounted into `main.app` needs the same two-sided check before it's assumed to work, not just a happy-path test against an isolated bare app.

- `coderfleet/server/main.py` — FastAPI app defining all REST endpoints and WebSocket terminal handlers; wires the Telegram bridge and usage-polling loops at startup. `create_task` resolves account/project by fixed precedence — `account` param > `project` (mounted-path match) > `type` > first idle account — and must check `scheduler.conversation_queue_full(req.conversation_id)` before calling `scheduler.submit`; `MAX_PENDING_PER_CONV` is imported from `scheduler.py`, never redefined locally, since a prior local recount in main.py drifted out of sync with an equivalent check in `telegram_bridge.py` (fixed in `b315ea7`). `reconcile_tasks_on_startup` requires `telegram_bridge.start_polling()` to run before `scheduler.reconcile_running_tasks()`, so the bridge is wired before any reconciled task can complete and try to notify through it. Both WebSocket terminal handlers (`project_terminal`, `conversation_terminal`) share one shape — origin check → accept → `asyncio.wait(FIRST_COMPLETED)` over paired input/output pump tasks → cancel loser → `session.close()` — and the tmux variant treats close as detach, not kill, so the session outlives the socket; `_is_allowed_terminal_origin` is the sole CSRF-style guard on that upgrade and allows a missing Origin header outright. `_serve_project_file` is the only path-traversal guard for downloads (`target.relative_to(base_dir)` must succeed); `download_task_file` feeds it a path resolved via `task.project_name` in preference to raw `task.project`, mirroring the project_name-precedence convention used elsewhere. Endpoints doing directory scans or subprocess calls (`docker inspect`, workflow-run listing, project/account listing) must run inside `run_in_threadpool` — added after synchronous versions blocked the event loop and starved concurrent SSE/WebSocket connections. Every `sched.updated`/`last_run_at`/`digest.generated_at`/`record.updated` assignment and the `/api/stats/usage` `cutoff` comparison use `now_iso()`/`utc_now()`/`parse_iso()` from `models.py`, not bare `datetime` — `main.py` no longer imports `datetime` at module scope at all (only a local `timedelta` inside `get_usage_stats`); re-adding a bare `datetime.now().isoformat()` anywhere here reintroduces the host/browser-timezone-dependent "刚刚 forever" bug fixed across `models.py`/`scheduler.py`. `stream_logs`'s continuous polling loop buffers cross-iteration bytes via `log_parser.split_complete_lines` before decoding/yielding — same UTF-8-character-corruption class as `scheduler.py`'s host-log poller (see that file's entry). The one-time `skip_bytes`/`tail` initial reads (inside `stream_logs`) and `get_logs`'s (`GET /api/tasks/{id}/logs`) full-file read are **not** exempt from this even though `log_path` only ever grows in complete-line increments — `_stream_container_log`'s writer only guarantees the *content* it persists ends on a real newline, not that a concurrent reader observes the underlying `write()` syscall atomically; a large chunk (a big `tool_use_result`/long reply) can still be caught by a same-instant read mid-flush, handing that reader a torn trailing line that then fails `JSON.parse` client-side and degrades to `renderer.js`'s raw/garbled `_rawLine` display — a real Web UI bug reported against a live conversation, not a hypothetical. All three one-shot reads (`get_logs`, and both of `stream_logs`'s `skip_bytes>0`/`tail>0` branches) now run their raw bytes through `log_parser.split_complete_lines` before decoding, same as the polling loop; `get_logs` only applies the trim when `task.status == TaskStatus.running` (a finished task's log is static, and its true last line may legitimately lack a trailing newline — trimming unconditionally there would silently drop it), while the two `stream_logs` branches always trim and carry the held-back tail into `pending` so the following polling iteration stitches it back together instead of losing or duplicating it. `trigger_digest_generation` (`POST /api/digest/{date}/generate`) checks `DIGEST_ENABLED` from `config.conf` (`_truthy(_load_config(...))`, default off) and raises `403` before doing anything else — same reason as `scheduler.py`'s `_check_auto_digest` gate: digest generation is a real task submitted into an active project's own container (`auto=True`), not a sandboxed summarizer, so it can write files into that project. The two gates are independent call sites reading the same `DIGEST_ENABLED` key — keep them in sync if the gating condition ever changes. `answer_task_intervention` (`POST /api/tasks/{id}/answer`, issue #69 Slice 1) is a thin wrapper over `scheduler.resolve_intervention` — all it does is translate `ValueError`→404 (task doesn't exist, or has no pending question matching that `tool_call_id`) and `RuntimeError`→409 (token mismatch, or the question was already answered/timed out); the `TaskAnswerRequest` body's `answers` dict is passed through untouched into exactly the shape `renderer.js`'s existing `_fillAskUserAnswers` already parses, so no format translation happens at this layer either. Deliberately mirrors `kill_task`/`update_task`'s 404/409 convention, not `approve_workflow_run`'s 400/409 one — see `scheduler.py`'s `resolve_intervention` entry for why those two "pause and wait for a human" mechanisms intentionally use different HTTP semantics for the same "token mismatch" case. Issue #69 Slice 2 mounts `mcp_bridge.build_intervention_mcp(scheduler).streamable_http_app()` at `/mcp` — the actual tool registration lives in the separate `mcp_bridge.py` module (see its own entry for why: this file's own `from __future__ import annotations` breaks FastMCP's tool-signature introspection). Mounting via `app.mount()` does **not** run the mounted sub-app's own lifespan (a documented Starlette/FastMCP gap, confirmed against `modelcontextprotocol/python-sdk#1367`) — without manual wiring the MCP session manager's task group would never start and every `/mcp` request would hang forever. `reconcile_tasks_on_startup` therefore also does `app.state.intervention_mcp_session_ctx = intervention_mcp.session_manager.run()` + `await ...__aenter__()`, with the matching `await ...__aexit__(None, None, None)` moved into a new `@app.on_event("shutdown")` handler (this file's first) — the two must stay paired; adding a second mounted MCP server anywhere else in this app needs the identical manual enter/exit treatment, `app.mount()` alone is not enough. `start_project_container`/`stop_project_container` and `docker_ops.py`'s CLI `up`/`down`/`restart <project>` must resolve a project's IDE proxy sidecar service (`compose.ide_service_name()`) alongside its main service whenever `ide_enabled` is set — `compose.py`'s generator adds that sidecar as a second compose service, but these three call sites previously only knew the main service name, so toggling IDE on in the project editor and restarting just that project never created the sidecar; only a full `apply` (which starts every service unconditionally) did. Any future project-scoped sidecar added to `compose.py` needs the same three call sites updated, not just the generator.

- `coderfleet/server/mcp_bridge.py` — Issue #69 Slice 2's MCP server: `build_intervention_mcp(scheduler)` returns a `FastMCP("coderfleet", streamable_http_path="/")` with one registered tool, `ask_user_question`, whose wire name to Claude is `mcp__coderfleet__ask_user_question` (must stay in sync with `renderer.js`'s `ChatLogRenderer.INTERVENTION_TOOL_NAME` and `account_type_registry.py`'s `_claude_mcp_bridge_arg`). Deliberately its own module, NOT folded into `main.py`: FastMCP's `Tool.from_function` does `issubclass(param.annotation, Context)` directly on raw `inspect.signature()` output without resolving PEP 563 string annotations first, so registering a tool from any module carrying `from __future__ import annotations` (which `main.py` has, file-wide) throws `TypeError: issubclass() arg 1 must be a class` for *every* parameter, not just `Context`-typed ones — confirmed by actually running it, not assumed from docs. `streamable_http_path="/"` is required alongside `main.py` mounting this app at `/mcp` — FastMCP's own default path is *also* `/mcp`, so leaving both un-overridden makes the real reachable path `/mcp/mcp`, silently 404ing (also empirically caught, not assumed). The tool takes `ctx` via `mcp_server.get_context()` inside the function body rather than a `ctx: Context` parameter — same PEP-563 issue as above would otherwise misfire on this one parameter even in a future-import-free file if it were typed directly, since `get_context()` sidesteps the auto-detection path entirely; it's also how the code reads the incoming `X-CoderFleet-Task-Id` header via `ctx.request_context.request.headers`. Tool input is typed `list[InterventionQuestion]` (from `models.py`), not a bare `list[dict]` — FastMCP derives the tool's JSON schema Claude actually sees from this type, so using the real Pydantic model (not an untyped dict) is what makes the schema match CC's native `AskUserQuestion` shape (question/header/multiSelect/options) closely enough for the model to construct correct calls; a `/matt-code-review` Spec pass is what caught the original `list[dict]` version as only a partial match. Authenticating *which task* is calling is deliberately just the task id in a header, not a secret — see the tool's own docstring for the accepted trust-boundary trade-off (any container reaching the bridge could in principle spoof another task's id and create a bogus `PendingIntervention` on it; this does not touch the real secret, `PendingIntervention.token`, which still gates the human-answer side from Slice 1) and why closing it fully isn't worth a second token layer given this project's actual threat model (one operator's own accounts, not an external attacker). Verified end-to-end with a *real* `mcp` client (`ClientSession`/`streamablehttp_client`) over `httpx.ASGITransport` in `tests/test_mcp_bridge.py` — no real Docker/network needed, since ASGI-in-process is enough to drive the genuine wire protocol; this is real, checked-in coverage of exactly the layer issue #69's PRD originally called "deliberately outside the test seam" (that assumption predates Slice 2 actually being built — it turned out to be testable). `pyproject.toml` pins `mcp==1.12.4` and `sse-starlette<2.2.0` specifically, not the latest available — newer `mcp` (1.15+) requires `pydantic>=2.11`, and newer `sse-starlette` (2.2.1+) requires `starlette>=0.41.3`, both incompatible with this project's pinned `fastapi==0.115.0`/`pydantic==2.9.2`/`uvicorn==0.30.6`; verify any future `mcp` bump against these three pins via `uv lock --dry-run` before touching the version, the same way this one was checked in. The tool passes `tool_call_id=` through to `scheduler.wait_for_intervention_answer` by reading `ctx.request_context.meta.model_extra.get("claudecode/toolUseId")` — this is Claude Code's own tool_use id, sent via the MCP request's `_meta` field, and it's load-bearing: without it, a fresh random id gets minted instead and the Web UI card (keyed by that same CC tool_use id) can never match the `pending_intervention` it fetches when the user clicks submit — this was a real, 100%-reproducible bug found against a live deployment, not a timing edge case. `meta` can be `None` (client sent no `_meta` at all) and the key can be absent even when `meta` is present (older/other MCP clients) — both fall back to a random id via `wait_for_intervention_answer`'s own default, degrading to "works, but the Web UI card can't correlate precisely" rather than failing. Testing note: `tests/test_mcp_bridge.py`'s test for this sends the raw JSON-RPC body by hand rather than through `mcp.types.CallToolRequestParams(meta=...)` — that class combines `model_config = ConfigDict(extra="allow")` with `Field(alias="_meta")`, and pydantic 2.9.2 (this project's pinned version, confirmed in isolation with a minimal repro) has a real bug where that specific combination silently serializes the value under the plain field name instead of the alias, so a request built through the SDK's own model never puts `_meta` on the wire correctly at all. This is a bug in the *test client's* dependency stack, not in real Claude Code (a different codebase, not built on this SDK/pydantic combination) and not in this file's server-side extraction, which correctly reads a properly-formed incoming request either way.

- `coderfleet/server/scheduler.py` — Core task queue: resolves account/project, spawns tasks as detached `docker exec` processes, tracks state via `tasks/*.json`, drives conversation/session chaining and workflow execution. Dispatch is snapshot-then-recheck, not lock-based: `schedule_next_tasks` scans a `Task.load_all` snapshot once per 1s tick, but `_start_pending_task` re-reads the task from disk and bails unless it's still `pending`, closing a race where a task is killed between scan and dispatch (regression-tested: `test_start_pending_task_skips_when_cancelled_before_dispatch`). At most one task per `conversation_id` may be in flight at a time — enforced via `busy_conv_ids` ∪ `in_flight_conv_ids` within a scheduling pass plus a hard reject in `ensure_conversation_available` — because native `--resume` session chaining assumes exactly one CLI process per conversation. `depends_on` gates dispatch: pending on any unfinished dependency, cascades to `failed` if a dependency is `None`/`failed`/`killed`, dispatches only once all deps are `done`. Account resolution never silently falls back — mismatched explicit `account_name` vs. a project's bound account raises `ValueError` — and secondary accounts (`project.secondary_accounts`) never enter task dispatch, existing solely to mount extra CLI credentials; the enforced invariant is that no two accounts on a project, primary or secondary, share a `type`. `find_project_for_path` resolves nested projects by longest-prefix match so a child project always wins over its parent workspace root. `_stream_container_log` captures `native_session_id` from only the first log chunk that yields one and persists it immediately to both the task and conversation, so a killed task still leaves a resumable session id. It polls `host_log`'s byte size every 0.3s and copies new bytes to `log_path` via `_write_chunk`, buffering in `pending: bytes` across iterations and flushing only through `log_parser.split_complete_lines` — never decode/write a byte range that doesn't end on a `\n`. This isn't optional tidiness: decoding a raw byte-range chunk that happens to end mid-multi-byte-UTF-8-character (routine — task content here is frequently Chinese) replaces that character with U+FFFD garbage on **both** sides of the cut via `errors="replace"`, and no amount of later string concatenation can undo it; if the corruption lands near a JSON structural byte the whole line fails to `JSON.parse` client-side and degrades to raw/garbled display in the Web UI (`renderer.js`'s `_rawLine` fallback) — this is what a real incident looked like after CC's `tool_use_result` payloads grew large enough to make an unlucky mid-character poll tick likely (bigger lines take longer to write, giving more polls a chance to land mid-line). Regression test: `test_stream_container_log_does_not_corrupt_utf8_char_split_across_poll_tick` in `tests/test_runtime.py`, which reproduces the exact `���` corruption via a call-counted fake `asyncio.sleep` (deterministic, not a real-time race) — remove the `split_complete_lines` buffering and this test fails immediately. `pending` must be force-flushed once `is_done` — a final line with no trailing newline would otherwise sit in memory and never reach disk. `main.py`'s `stream_logs` SSE tail independently applies the same `split_complete_lines` buffering to its own continuous-polling loop as defense in depth, even though it reads from `log_path` (which this function now guarantees only ever grows in complete-line increments) rather than `host_log` directly. On restart, `reconcile_running_tasks` must check `is_task_process_alive` (a `pgrep`-matched marker string, `coderfleet-task-<id>`, not PID — PIDs aren't stable across `docker exec` reattachment) before trusting a host `.exit` file — a live process always wins and gets reattached rather than treated as exited; this must run before anything else touches `running` tasks on startup. `kill_task` flips status to `killed` before cancelling the asyncio task ("update status first to prevent concurrent writes"), then awaits `bg.cancel()` under `asyncio.shield` with a 3s timeout so the task's own `CancelledError` cleanup still runs. `build_cli_command`'s `( ... )` subshell wrapping is load-bearing: it lets `exec -a` replace only the inner subshell so the outer wrapper can still capture `$?` after exec — don't flatten it. `MAX_PENDING_PER_CONV = 5` is the single shared cap consumed by both the API and the Telegram bridge via `conversation_queue_full` — do not reimplement it locally elsewhere. Usage probing always runs inside the account's own container, never bare from the host — hitting the vendor API sometimes via proxy, sometimes not, risks anti-abuse flags. Two timestamp regimes coexist here on purpose, do not merge them: (1) audit/display fields (`Conversation.updated`, `WorkflowRun.updated`/`NodeExecution.started_at`/`finished_at`, `Schedule.updated`/`last_run_at`, `ephemeral_expires_at`, `AccountUsage.fetched_at`) are generated via `now_iso()`/`utc_now()` and read back via `parse_iso()` (all from `models.py`) so they're UTC-aware and safe to compare/sort regardless of host timezone — `pending_tasks.sort()` in `schedule_next_tasks` and `list_workflow_runs`'s sort both parse through `parse_iso()` rather than comparing raw strings, since raw-string comparison silently breaks across the naive→aware migration boundary; (2) `_compute_next_run_at`/`_check_and_trigger_schedules`/`_validate_future_execute_at`/`schedule_next_tasks`'s `execute_at` check, and `_check_auto_digest`'s 23:30 gate, intentionally keep using bare naive `datetime.now()` — schedule/cron wall-clock math (`time_of_day="14:30"`) is defined in the scheduler host's local time by design, and converting it to UTC would fire schedules at the wrong wall-clock hour, not just cosmetically mis-format a display string. `_check_auto_digest` checks `DIGEST_ENABLED` (config.conf, default `off` via `truthy()`) *before* the 23:30 time check, not after — generating a digest submits a real prompt-only task into the first active project's own container via `self.submit(..., auto=True)`, which can end up writing files into that project's working tree since it's a live CLI session, not a sandboxed summarizer; the config check must stay first so the gate is time-independent and testable without faking `datetime.now()` (`test_check_auto_digest_skips_when_digest_disabled`). `wait_for_intervention_answer`/`resolve_intervention` (issue #69 Slice 1) are the core of **Intervention** — a non-`auto` task's CLI pausing mid-run to ask a human a structured question (schema-identical to Claude Code's native `AskUserQuestion`, so `renderer.js` can eventually reuse that card unmodified — Web UI wiring itself is Slice 3, not done yet). This is a different shape of "pause and wait for a human" than `_wait_for_approval`/`approve_workflow_run` just above: that one polls (`asyncio.sleep(3s)` loop over a scheduler-internal coroutine watching scheduler-internal disk state), this one blocks on an in-process `asyncio.Future` keyed by `f"{task_id}:{tool_call_id}"` — polling would only add latency here since the waiter (the real MCP tool handler as of issue #69 Slice 2, see `mcp_bridge.py`'s entry — this slice's own tests still simulate it directly rather than going through the real MCP wire protocol) and the resolver (`resolve_intervention`, called from `POST /api/tasks/{id}/answer`) run in the same process and can signal each other directly. The Future is deliberately **not** popped from `self._pending_intervention_futures` once it completes (resolved or timed out) — `future.done()` staying `True` afterward is the only way `resolve_intervention` can distinguish "this `tool_call_id` never existed" (404, `ValueError`) from "it existed but was already answered/timed out" (409, `RuntimeError`) for a late-arriving answer; only `Task.pending_intervention` itself gets cleared (atomic read-modify-write, reloading and checking the `tool_call_id` still matches before writing, so a concurrent unrelated write to the task isn't clobbered). This means `_pending_intervention_futures` grows by one small entry per Intervention ever created for the life of the process — accepted as a minor, bounded-by-task-volume tradeoff, not a real leak concern. A scheduler restart mid-wait loses the in-memory Future entirely; the blocked caller on the other end (once real) has almost certainly already failed by the time the process comes back, so that specific pending call can't be recovered — `Task.pending_intervention` staying on disk is only so the UI/CLI/audit trail can show "a question was pending here," not to make the wait itself restart-safe (see issue #69's "Further Notes" for the accepted-limitation writeup). `resolve_intervention` raising `RuntimeError`→409 for a bad token is a deliberate divergence from `approve_workflow_run` raising `ValueError`→400 for the same conceptual case — issue #69's PRD groups "wrong token" and "already resolved/timed out" into the same 409-conflict semantic ("this was valid, but not now/not like this"), not a 400 malformed-request one; don't silently align the two, they encode different HTTP semantics on purpose. `coderfleet task answer` (`task_cmds.py`) and `cmd_task_status`'s `pending_intervention` display are the CLI-parity half of this same feature. `wait_for_intervention_answer`'s `tool_call_id` param (optional, defaults to a fresh `uuid.uuid4().hex` when omitted) exists because of a real bug found against a live deployment, not a hypothetical: the Web UI's question card is keyed by Claude's own `tool_use.id` from the JSONL log stream, but before this param existed the function always minted its own random id for `PendingIntervention.tool_call_id` — the two could never match, so every real answer submission failed with "this question is no longer waiting," 100% of the time, not just on timeout/races. `mcp_bridge.py`'s tool handler passes CC's own id through here (extracted from the MCP request's `_meta`); see that file's entry for exactly how.

- `coderfleet/server/models.py` — Pydantic domain models (Account, Project, Task, Conversation, Board/BoardCard, ImageBuild, Pipeline/WorkflowTemplate/WorkflowRun, Schedule) and their HTTP request/response shapes; single source of truth for record shape across CLI, scheduler, and Web UI. `Task.project`/`project_name` and `Conversation.project`/`project_name` are deliberately duplicated, not redundant: `project` is the host path, `project_name` the config name, and disambiguation code across `scheduler.py` branches on `project_name` truthiness before falling back to path matching — never collapse these. Every `*Response.from_*` classmethod reads newer fields via `getattr(obj, "field", default)` rather than direct access, a deliberate backward-compat guard for records loaded from pre-migration on-disk JSON; new fields need a concrete default and should follow this convention if read in a `from_*` method. Dead fields removed in `0aca8a3` (#32) — `Board.project_name`, `WorkflowRun.template_version`, and the `artifact_sync` workspace-policy value — must not be re-added; they were write-only or unimplemented placeholders. `Project.secondary_accounts` performs no validation itself (the one-account-per-type-per-project rule lives in the CLI/API layer) and is never read by `Task`/`Conversation`, which stay bound to the primary `account` only. `Pipeline` is explicitly marked deprecated (internal execution-engine state only, no user-facing create routes); `WorkflowRun` is the live v2 entity and was added purely additively so legacy `Pipeline`/`WorkflowTemplate` records keep parsing. `TaskHeartbeat` is deliberately minimal (id/status/conversation_id/finished only) for 5-second polling — do not add heavy fields like `prompt`/`images` to it. `TASK_STATUS_LABELS` (added in `b315ea7`) is the single shared map from terminal `TaskStatus` to notification title/broadcast-eligibility, used by both Web Push and Telegram — don't duplicate this set elsewhere. `now_iso()`/`utc_now()`/`parse_iso()` are the single source for every `created`/`updated`/`finished`/`started_at`/`finished_at` field on every model here — never call bare `datetime.now().isoformat()` again. Root cause: a naive (tz-less) timestamp gets parsed by the browser as local-browser-time, so any skew between the host running `coderfleet server` and the browser's clock/timezone could push it into the apparent future, and the frontend's `fmtTime()` had no floor on negative diffs — it stuck on "刚刚" forever instead of ever ticking over. `now_iso()` emits UTC-aware ISO strings (`+00:00` suffix) so display no longer depends on host/browser timezone agreement; `parse_iso()` is the required read-side counterpart — it transparently upgrades pre-migration naive strings already on disk (assumes host-local, matching their original semantics) so aware/naive values never get compared directly (`TypeError`) or sorted as raw strings across the migration boundary. `InterventionOption`'s `model_validator(mode="before")` coercing a bare string into `{"label": <string>}` exists because of a real failure seen against a live deployment (issue #69): Claude's first guess at the `ask_user_question` tool call passed `options` as a plain string array instead of `{label, description}` objects — a reasonable guess for a schema it's never seen, but one Pydantic's strict validation rejected outright (5 validation errors surfaced to the human as a raw traceback in the chat log) before the model self-corrected and retried successfully. A bare string is semantically unambiguous as a label, so it's accepted directly rather than making every model guess the full object shape on the first try.

- `coderfleet/account_type_registry.py` — Single registration point for CLI account types (`claude`/`codex`/`opencode`/`hermes`/`grok`/`kimi`/`pi`); `compose.py`, `login_cmd.py`, `scheduler.py`'s command-building, `config_cmds.py`, `server/models.py`'s `AccountType` enum, and the Web UI account cards all derive account-type behavior from `ACCOUNT_TYPES` generically — adding a type means adding one `AccountTypeSpec` entry here, never a new `if acc_type == "..."` branch in those files. `AccountType` is derived from `ACCOUNT_TYPES.keys()` at import time — never hand-declare a parallel `AccountType(str, Enum)`, it would drift the moment a type is added/removed here (same class of duplication `b315ea7` fixed for `TASK_STATUS_LABELS`/`MAX_PENDING_PER_CONV`). `env_auth_type_ids()`/`valid_type_ids()` are the only sanctioned way to enumerate types outside this module. Each `_build_<type>`/`_extract_<type>`/`_events_<type>` function must stay pure (no I/O) — that's what makes them directly unit-testable without Docker (`tests/test_account_type_registry.py`). `pi`'s `_build_pi` maps CoderFleet's `auto` flag to pi's `--approve`/`--no-approve` (project-trust for loading `.pi/` config), not a real permission gate — pi has no tool-confirmation system by design, its own container is the safety boundary it expects, so `auto` does not toggle "restricted vs. unrestricted" tool execution for pi the way it does for `claude`/`codex`. `_build_pi` attaches `images` as `@path` positional args (pi's real attachment mechanism, per its own docs — for images this sends actual multimodal bytes, not just a path) — do NOT "fix" this to match `claude`/`grok`/`kimi`'s convention of folding image paths into the prompt text as a `[Attached images: ...]` hint; that convention exists only because those CLIs lack a native attachment flag, pi has one and it's strictly better. `AccountTypeSpec.parse_output_events` (issue #70) is a fourth per-type pure function, alongside `build_inner_cmd`/`extract_session_id`, that classifies one decoded task-output JSON line into a small closed vocabulary of `OutputEvent`s (`TextChunk`/`FinalText` for text; `UsageDelta`/`UsageProgress`/`UsageTotal` for token counts; `CostDelta`/`CostFirstSeen`/`CostTotal` for cost — each with exactly one fixed combination rule, applied generically by `server/log_parser.py`'s `_apply_event`, not re-decided per type). Issue #74 extended the vocabulary past text/usage with `ToolIntent`/`ToolOutcome`: a tool call's **request and its result are always two separate events** correlated by `call_id`, never one combined event, because every real format splits them across lines (three of them under different field names) and collapsing them would force classifiers to carry state across lines — destroying the purity that makes them testable without Docker. What's normalized is the correlation id's *field name*, not its value (`tool_use_id`/`tool_call_id`/`toolCallId` all land on `call_id`); the value is passed through verbatim since it's only ever compared for equality inside one log. `arguments` is always a `dict` by the time it leaves a classifier — formats that JSON-encode it as a string decode it there, so consumers see one shape. These two members deliberately fold to **nothing** in `TaskOutputData`; their real reader is `log_parser.detect_unrecognized_shapes`. Two further fields exist only to serve that detector: `shape_of` (a pure line→shape-name function, defaulting to `_shape_by_type`) and `silent_shapes` (the frozenset of shapes that produce no events *by design*). `shape_of` is per-type and **must not be hardcoded to `type`** anywhere — `claude`/`codex`/`opencode`/`pi` discriminate on `type` but `kimi` discriminates on `role`, using `type` only to sub-classify its `meta` lines. `kimi` has **not** had its own `shape_of` declared yet (that lands with its classifier slice) and so currently inherits `_shape_by_type`, which collapses every kimi line into one meaningless bucket — the detector is not usable for `kimi` until that slice sets `shape_of=` on its entry. That the mechanism *can* express a non-`type` discriminator without the detector changing is proven now rather than then (`test_detect_unrecognized_shapes_honours_a_non_type_discriminator`), because finding out otherwise at the kimi slice would mean reworking every classifier slice in between. Both fields sit on the same registry entry as `parse_output_events` so a classifier and its coverage declaration cannot drift apart; the vetted starting list for a type's `silent_shapes` is the set of explicit no-op cases in that type's `renderer.js` switch — anything declared *beyond* that set widens the detector's blind spot and must carry its own written reason (`_SILENT_PI` adds two: `session`, which nothing classifies and would otherwise be a permanent false positive on every log, and `agent_end`, whose silence is the deliberate anti-double-counting choice described above). As of #74 only `pi` classifies tool calls (`_SILENT_PI` is the one declared set); `claude`/`codex`/`opencode`/`kimi` are follow-on slices of #71, and `grok` genuinely has no tool surface (asserted by test, not assumed — "this format has no tool events" is otherwise indistinguishable from "we forgot", which is the mistake #71's own text made about `kimi`). `server/log_parser.py` now derives its dispatch from this field (`ACCOUNT_TYPES.get(acc_type).parse_output_events`) instead of hardcoding its own six-way branch, closing the gap that shipped broken for `pi` (missing output-parsing branch, silent raw-JSON/zero-usage fallback) and drifted twice for `codex`/`opencode` before that. `hermes` leaves this field unset (`None`) — it's plain text, not JSONL, and stays on `log_parser.py`'s generic `_parse_text_fallback`. **`server/static/js/renderer.js` is still NOT wired to this registry** — its live Web UI rendering hardcodes its own separate per-type event switch (see that file's own entry) and was deliberately left out of issue #70's scope, since no JS test harness exists yet to refactor it against safely; a new account type still needs its own `renderer.js` branch or it will render raw/empty in the Web UI even though `parse_output_events` now makes its logged text/usage correct everywhere else. `_claude_mcp_bridge_arg` (issue #69 Slice 2) builds the `--mcp-config`/`--allowedTools mcp__coderfleet__ask_user_question` fragment `_build_claude` appends whenever `not auto` — deliberately a private helper called only from `_build_claude`, not a new field on `AccountTypeSpec`, since the per-type extension already lives naturally in each type's own `_build_<type>` function and a registry field would only ever be non-`None` for one type right now; add the Codex/OpenCode equivalents the same way (inline in their own `_build_<type>`) if/when they're wired, not by promoting this to a dataclass field speculatively. Takes **no arguments** and is byte-identical for every call — a `/matt-code-review` Spec pass caught an earlier version that took `task_id` and interpolated it directly into the JSON (violating the PRD's explicit "no per-task JSON composition" requirement); it now references `${CODERFLEET_RELAY_IP}`/`${CODERFLEET_MCP_BRIDGE_PORT}`/`${CODERFLEET_TASK_ID}` entirely via Claude's own `${VAR}` config-expansion syntax, resolved from environment `compose.py`/`_build_claude`'s own `CODERFLEET_TASK_ID={task_env}` prefix already provide — not by this function. The relay vars use `${VAR:-default}` fallbacks (not bare `${VAR}`) specifically so a `PROXY=off` account (which never gets those two env vars from `compose.py`) still gets a syntactically-valid config and a normal Claude startup; without the fallback, Claude would fail to parse `--mcp-config` at all and the whole task would refuse to start over a feature it was never going to use, instead of the intended much smaller failure (a clean "tool execution failed" if the model ever actually calls the bridge tool while relay vars are unset). Only wired when `auto=False` — `auto=True`'s contract is "decide on your own, don't ask," so it must never see this tool. `--permission-mode acceptEdits` (the existing non-auto flag) only auto-approves file-edit tools, not MCP calls, hence `--allowedTools` is required alongside `--mcp-config`, not implied by it. Known, accepted trust-boundary gap (see `mcp_bridge.py`'s own entry): the bridge call itself is identified only by the task id in a header, unsigned — see that file's docstring for why this is an accepted trade-off rather than a bug to fix here.

- `coderfleet/server/log_parser.py` — Parses a completed task's raw log into `TaskOutputData` (final text + token/cost usage), consumed by `GET /api/tasks/{id}/output` (workflow `{{steps.X.outputs.text}}`), `scheduler.py`'s `_extract_and_save_token_usage`, and Digest AI-summary capture. `parse_log()` no longer hardcodes a per-type branch table (issue #70): it looks up `ACCOUNT_TYPES.get(acc_type).parse_output_events` — a pure per-type classifier owned by `account_type_registry.py` — and folds the normalized `OutputEvent`s it returns into `TaskOutputData` via one generic `_apply_event`, whose `isinstance` chain implements exactly one fixed combination rule per event kind (`TextChunk` appends, `FinalText` overwrites, `UsageDelta` adds both sides, `UsageProgress` maxes input/adds output, `UsageTotal` overwrites each non-`None` side independently, `CostDelta` adds, `CostFirstSeen` sets only if unset, `CostTotal` overwrites) — applied the same way regardless of which account type produced the event. `ToolIntent`/`ToolOutcome` (issue #74) have an **explicit no-op branch** in that chain rather than falling off its end, so the silence reads as deliberate: `TaskOutputData` models a finished task's answer and its price, and folding a tool call into `text` would corrupt the value workflows substitute into `{{steps.X.outputs.text}}` — do not add a field for them here. A new account type's output-parsing support is therefore entirely a matter of writing one `_events_<type>` function in `account_type_registry.py`; this file never needs a new per-type branch again. `detect_unrecognized_shapes(log_text, acc_type) -> ShapeCoverage` (also #74) is the actual consumer of the tool events and the only reader of the registry's `shape_of`/`silent_shapes`: it groups a log's lines by that type's shape discriminator and reports every shape that produced zero `OutputEvent`s on **every** one of its occurrences and isn't declared silent. Silence is judged per shape across the whole log, never per line, because one shape legitimately classifies on some lines and not others (`pi` emits `message_end` for user turns as well as assistant ones) — detection granularity is therefore whatever a type's `shape_of` gives, and a type needing finer resolution sharpens its own `shape_of` rather than the detector gaining a branch. `ShapeCoverage` carries `acc_type` alongside the counts because shape names collide across formats (`text`, `message_end`, `assistant` all appear in more than one), so a bare shape name isn't actionable. This detector could not have existed before tool calls were classified — almost every line in a real log used to produce zero events, making "produced nothing" pure noise — and it is exactly what would have caught both prior silent breakages below. It's pure, never raises (unknown `acc_type` and classifier-less `hermes` both report an empty `ShapeCoverage`), and is deliberately **not** wired into the scheduler or server: choosing an enforcement policy (warn/fail/rate-limit) is a separate decision, and its consumer today is the test suite. `hermes` has no `parse_output_events` registered (plain text, not JSONL) and always falls through to `_parse_text_fallback`, same as any account type whose events happen to yield no text on a given log. This replaced six independently hand-maintained `_parse_<type>_line` functions that did not derive from `ACCOUNT_TYPES` and had already drifted twice in production: `pi` shipped with no output-parsing branch at all (silent raw-JSON dump, zero usage), and `codex`/`opencode` both independently kept matching a stale flat event shape (`type:"message"` + top-level `content`/`usage`) after their CLIs had moved on to `item.completed`'s `item.type==="agent_message"` text + `turn.completed.usage` (codex, cumulative-not-delta) and `part`-nested `part.text`/`part.tokens` (opencode) respectively — zero test coverage caught either drift until found by hand. Each account type's real-log shape now has both a black-box regression fixture here (`tests/test_log_parser.py`, asserting on `parse_log()`'s output — this suite is the behavior-preservation proof for the issue #70 refactor and must keep passing with unmodified expected values) and a direct pure-function unit test on its `_events_<type>` classifier (`tests/test_account_type_registry.py`). `server/static/js/renderer.js`'s live Web UI rendering still hardcodes its own separate, independent per-type event vocabulary — issue #70 deliberately left it out of scope, since no JS test harness exists yet to refactor it against safely — so a new account type still needs a `renderer.js` branch of its own even after registering `parse_output_events` here; see that file's entry. Also hosts `split_complete_lines(buf: bytes) -> (complete, pending)`, a tiny line-boundary-safe helper shared by every place that tails a growing log file in byte chunks — `scheduler.py`'s `_stream_container_log` (host_log → log_path) and every one-shot/polling read in `main.py` (`get_logs`, and both branches of `stream_logs`'s cold start plus its polling loop) import it rather than reimplementing the same "don't decode/emit a byte range that doesn't end on a real newline" check locally; see `scheduler.py`'s and `main.py`'s entries for why a *reader* needs this guard even when the writer already only ever persists complete lines (mid-UTF-8-character corruption and torn-write visibility, not just cosmetic line-splitting).

- `coderfleet/server/static/js/renderer.js` — `ChatLogRenderer`, the Web UI's task/conversation log viewer. Per-type event vocabulary is hardcoded and does NOT derive from `account_type_registry.py` (unlike `server/log_parser.py`'s output-text/usage extraction, unified behind `AccountTypeSpec.parse_output_events` in issue #70 — this file was deliberately left out of that PRD's scope, since no JS test harness exists yet to refactor it against safely) — a new account type needs its own `case`s in `_event()`'s switch (or a dedicated `_<type>Line()` parser routed from `_processLine()`, the pattern used for `hermes`/`grok`/`kimi` because their formats aren't single-line-JSON-per-event). Issue #69 Slice 3 (Web UI live-answering) added `ChatLogRenderer.INTERVENTION_TOOL_NAME` (`mcp__coderfleet__ask_user_question`, the MCP wire name of the Slice-1 bridge tool) as a second trigger for `_toolUseAskUserQuestion` alongside CC's native `'AskUserQuestion'` — both share the same card, but `_toolUseAskUserQuestion`'s `displayName` normalizes the ugly wire name back to `'AskUserQuestion'` for display, and `isLive` (`isIntervention && this.isRunning`) gates whether `_buildLiveAskqInputs` renders actual radio/checkbox/free-text controls instead of the read-only "等待作答…" placeholder — native AskUserQuestion never goes live, since CoderFleet has no backend that can answer it. `isLive` is deliberately derived from "no `tool_result` seen yet for this `tool_use.id`" rather than from a fresh read of `Task.pending_intervention` at render time — a Task can only have one open Intervention at once (enforced by `scheduler.py`'s one-`Future`-per-task design), so the two are equivalent, and the one place that genuinely needs authoritative freshness (submit time — token correctness, whether it's already been answered/timed out elsewhere) does fetch `GET /api/tasks/{id}` right before `POST /api/tasks/{id}/answer` (`_submitIntervention`). This is the one place `ChatLogRenderer` makes its own network calls at all (otherwise a pure JSONL→DOM renderer) — deliberate, not scope creep: `chat.js` and `mobile.html` are two fully independent front-ends sharing only this renderer class, so putting submit/error/retry handling here once is cheaper and less failure-prone than duplicating it in both; `this.taskId`, threaded through every constructor call site in both files, is what makes the renderer self-sufficient for this. `_fillAskUserAnswers` special-cases the Slice-1 timeout sentinel (`tool_result` content `{"timed_out": true}`) before its generic JSON-match/free-text-fallback logic and returns whether it hit that case — without this check the sentinel fell into the free-text fallback and rendered the raw `{"timed_out":true}` JSON as if the user had typed it as a free-response answer, with `_fillTool`'s exit label claiming "✓ 已作答" (answered) since the tool_result isn't flagged as an error; both call sites of `_fillAskUserAnswers` (there is only the one, in `_fillTool`) must keep using its return value for the exit label rather than re-deriving `ok` from `isError` alone. `deactivatePendingInterventions()` (called from both `chat.js`'s and `mobile.html`'s SSE `[DONE]` handlers) disables any still-live form and marks it "任务已结束，未作答" — mostly a belt-and-suspenders measure since the `[DONE]` handler's subsequent full workspace reload would re-render with `isRunning=false` anyway (no live form would be built fresh), but closes the brief window before that reload lands. The `.askq-live-*`/`.askq-submit-*` CSS rules are intentionally duplicated between `renderer.css` and `main.css`, matching this codebase's existing (pre-Slice-3) duplication of every other `.askq-*` rule across those two files — not a new pattern introduced here.

**The task board itself is a single sticky DOM node the whole render/push lifetime, mutated in place — not one card appended per event.** Originally each `TaskUpdate`/`TaskList` call appended a full new board card, so a session with 8 tasks and a dozen updates rendered the same ~8-row list a dozen times down the timeline; this was rebuilt (per product-design discussion, not a lobehub feature) around `_ensureTaskBoardEl()`/`_updateTaskBoardEl()`: the board element (`this.taskBoardEl` + cached `taskBoardIconEl`/`taskBoardLabelEl`/`taskBoardCountEl`/`taskBoardListEl` refs) is created once on the first `TaskCreate`/`TaskUpdate`/`TaskList` event and every subsequent one just rewrites its `textContent`/`innerHTML` in place; each individual `TaskUpdate`/`TaskList` event instead leaves a lightweight one-line `_pill()` marker at its actual chronological position in the timeline, so the narrative ("已开始: X", "已完成: X") is preserved without repeating the whole board. The board is deliberately appended directly to `this.inner` rather than through `_appendNode` — going through `_appendNode` while `foldProcess` is active would let it get folded into the collapsed "任务执行过程" wrapper (`display:none`), which defeats the entire point of a panel that must always stay visible. CSS: `.task-board-sticky` (`position: sticky; top: 8px`) makes it pin to the top of whichever scrolling ancestor contains it — verified against the real desktop chat layout (`#chat-viewport { overflow-y: auto }` → `#chat-content` → `.chat-log`, in `chat.js`); in contexts where no scrolling ancestor exists (a bare log-modal container, say) `sticky` degrades harmlessly to normal in-flow positioning, so this is safe to reuse across `chat.js`/`log.js`/`workflows.js`'s different container structures without per-context testing. `_renderTaskRowHtml` (single-row renderer) is shared between `TodoWrite` and the task board — same visual language, no new row-level CSS was needed, only the sticky-container chrome.

- `coderfleet/data/Dockerfile` — Single shared image for every account container; every pinned version here is fleet-wide. `ENV LANG=C.UTF-8`/`LC_ALL=C.UTF-8` must stay set (`2e3bdaa`) — without it bash readline mis-echoes multibyte UTF-8 (breaks Chinese input); Ubuntu 24.04 needs no `locale-gen` since C.UTF-8 ships with glibc. Python installs use `--break-system-packages` (Ubuntu 24.04 enforces PEP 668 on the system interpreter). Hermes installs into an isolated venv (`/opt/hermes-venv`) rather than system pip because apt-managed `PyJWT` has no RECORD file and can't be uninstalled by pip if they collide. RTK's installer verifies a SHA-256 checksum before extracting — a supply-chain check; don't swap for an unverified curl-pipe. `USER byclaw` must stay the very last line, after every root-requiring install (apt, playwright system deps) — moving it earlier breaks any subsequent root-only `RUN`. `npm install -g npm@<pinned>` must stay pinned to a specific version below npm/cli's `optionalDependencies`-skipping regression window (`>=11.5.0`, npm/cli #8464/#8628) — floating it back to `npm@latest` silently breaks any npm-installed CLI whose native binary ships as an optional dependency (bit `claude` this way: exits 0, binary just isn't there). Any edit to an *earlier* layer (e.g. the Node.js version line) invalidates Docker's build cache for every layer after it, including this one — an otherwise-unrelated Node bump can resurface this class of bug purely by forcing a fresh `npm@latest`-equivalent resolution; re-verify all npm-installed CLIs (`claude`/`codex`/`opencode`) after touching anything above this line.
