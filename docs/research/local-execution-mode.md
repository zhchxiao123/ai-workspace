# Can CoderFleet support a "local execution" mode — running Claude Code CLI and/or OpenAI Codex CLI directly on the host, outside any Docker container — including auto-detecting which CLIs are already installed?

Research date: 2026-08-03. All claims below are sourced from: (a) this repository's own code (`coderfleet/server/scheduler.py`, `coderfleet/server/runtime.py`, `coderfleet/server/models.py`, `coderfleet/account_type_registry.py`, `coderfleet/compose.py`), read directly and cited by file path + line number/function name; (b) official Anthropic Claude Code documentation at `code.claude.com/docs/en/*` (the current canonical docs host — `docs.anthropic.com/en/docs/claude-code/*` URLs 301-redirect there); (c) official OpenAI Codex documentation at `learn.chatgpt.com/docs/*` and `developers.openai.com/codex/*` (these two hostnames redirect to each other/interchange — the `openai/codex` GitHub repo's own `docs/sandbox.md` links `developers.openai.com/codex/security` as its canonical external reference, which is how this research treats `learn.chatgpt.com`/`developers.openai.com` as primary rather than secondary); (d) the `openai/codex` GitHub repository's `README.md` (fetched via `raw.githubusercontent.com`); (e) the exact `--help` output of both CLIs (`claude --help`, `claude auth --help`, `codex --help`, `codex exec --help`, `codex resume --help`, `codex login --help`), run directly in this research sandbox; (f) direct empirical observation in this research sandbox — both CLIs are installed here (`claude 2.1.220`, `codex-cli 0.146.0`), so several claims about config-dir isolation were verified by actually invoking the CLIs with overridden `CLAUDE_CONFIG_DIR`/`CODEX_HOME` values and observing the output, not merely inferred from docs. No blog posts, gists, Stack Overflow, or other secondary summaries were used as citations — several WebSearch results surfaced such secondary pages during research, but every claim below was re-verified against the primary doc, repo, or CLI output before being cited, and any claim that could not be so verified is explicitly flagged as unverified below rather than cited to a secondary source.

Note on this research sandbox: the environment this research was run in is itself already configured like a CoderFleet-managed container (`CLAUDE_CONFIG_DIR=/home/byclaw/.claude`, `CODEX_HOME=/home/byclaw/.codex`, `HTTPS_PROXY`/`ALL_PROXY` etc. all pre-set to CoderFleet's relay conventions — matching `coderfleet/compose.py` lines 229–230, 241–247 below). This does not invalidate CLI-behavior findings (the `--help` text and config-dir-override behavior are unaffected by whether the invoking shell happens to be inside a container), but it means "local host, no container" was not literally tested end-to-end in this sandbox — that gap is called out explicitly where relevant.

## 1. CoderFleet's current execution model (correcting/confirming the background brief)

- **A execution-backend seam already exists — the background brief's claim that there is "no execution-backend abstraction today" is only partially correct.** `coderfleet/server/runtime.py` defines a `ContainerRuntime` `Protocol` (`runtime.py:57`) with exactly four methods (`run`, `exec`, `is_running`, `remove`), a production `DockerRuntime` implementation (`runtime.py:75`) that is "唯一拼装 docker argv、真正调用 OS 的地方" ("the only place that assembles docker argv and actually calls the OS" — `runtime.py:76` docstring), and a test-only `FakeRuntime` (`runtime.py:195`). `Scheduler.__init__` takes an injectable `runtime: "ContainerRuntime | None" = None` parameter and defaults to `DockerRuntime()` (`scheduler.py:105-109`). The module docstring states the seam's purpose directly: "任务执行的两条路径（持久容器 `docker exec` 与临时容器 `docker run`）最终都落在同一个 OS 调用上...把「如何生成 docker argv 并启动子进程」收拢到一个接口后面" ("the two task-execution paths... both bottom out in the same OS call... collect 'how to build docker argv and start the subprocess' behind one interface" — `runtime.py:1-8`).
- **The main task-execution paths already go through this seam, not raw `asyncio.create_subprocess_exec`.** `self.runtime.run(...)`/`self.runtime.exec(...)` calls appear at `scheduler.py:2854`, `2894`, `2898`, `3021`, `3090` — these cover ephemeral-container startup, persistent-container-style ephemeral exec, and (by inspection of call sites) the main task dispatch path.
- **However, two auxiliary helper functions bypass the seam and hardcode `docker exec` directly, confirming the background brief's citation was accurate for those two call sites specifically.** `_get_hermes_session_id` calls `asyncio.create_subprocess_exec("docker", "exec", container_name, "bash", "-lc", ...)` directly at `scheduler.py:3234-3239` (this is the exact line the task brief pointed to). A second, adjacent hardcoded `docker exec` call (usage-status check) appears at `scheduler.py:3186-3195`. Both would need to be routed through `self.runtime.exec(...)` (or a new local-execution seam) to support a non-Docker backend.
- **`DockerRuntime.exec`/`.run` build literal `docker exec`/`docker run` argv strings and call `asyncio.create_subprocess_exec` on them** — `build_exec_argv` (`runtime.py:100-114`) and `build_run_argv` (`runtime.py:79-98`) are pure functions; `exec`/`run` (`runtime.py:117-133`) call `asyncio.create_subprocess_exec(*argv, stdout=PIPE, stderr=STDOUT)`. A hypothetical `LocalRuntime` implementing the same `ContainerRuntime` Protocol could instead call `asyncio.create_subprocess_exec(*command, env=merged_env, cwd=workdir, ...)` directly on the host, without `docker` in the argv at all — the Protocol's 4-method shape (`run`/`exec`/`is_running`/`remove`) does not itself reference Docker in its method signatures (`runtime.py:57-72`), so it is not structurally Docker-specific.
- **Account proxy setting**: `AccountProxy` enum is `relay | off` (`models.py:116-118`), and `Account.proxy: AccountProxy = AccountProxy.relay` (`models.py:128`) — confirming the background brief's description of `models.py:111-128` (the enum classes sit at exactly those lines).
- **Proxy env-var injection into containers happens in two places with identical variable sets**: `coderfleet/compose.py:239-250` (persistent containers, `docker-compose.yml` generation) sets `HTTP_PROXY`/`HTTPS_PROXY`/`http_proxy`/`https_proxy`/`ALL_PROXY`/`all_proxy`/`NO_PROXY`/`no_proxy` to a `proxy_url` built from `RELAY_IP`/`RELAY_LISTEN_PORT`, only `if acc_proxy != "off"`; `scheduler.py:2792-2805` (`_run_ephemeral_task`) does the same for ephemeral containers, reading `RELAY_IP`/`RELAY_LISTEN_PORT`/`NO_PROXY` from `load_config(self.workspace_dir)` and only setting these vars `if network:` (i.e. only for relay-networked ephemeral containers). This confirms the background brief's description of `scheduler.py:2790-2814` almost exactly (the actual proxy block is `2792-2805`; `2807-2814` sets the account-identity env vars `CODEX_HOME`, `CLAUDE_CONFIG_DIR`, `CODERFLEET_ACCOUNT_*` immediately after).
- **`CODEX_HOME` and `CLAUDE_CONFIG_DIR` are hardcoded to the *same* in-container path for every account** — `compose.py:229-230` sets `"CODEX_HOME": "/home/byclaw/.codex"` and `"CLAUDE_CONFIG_DIR": "/home/byclaw/.claude"` unconditionally (not per-account-name paths), and `scheduler.py:2808-2809` sets the identical two literals for ephemeral containers. Per-account isolation today comes entirely from each account getting its own **container** (with its own bind-mounted `accounts/<name>/` directory mounted at that fixed in-container path — `auth_src = self.workspace_dir / "accounts" / acc.name`, `auth_dst = spec.auth_dir`, `mounts.append((str(auth_src), str(auth_dst)))` at `scheduler.py:2759-2765`), not from giving each account a distinct `CODEX_HOME`/`CLAUDE_CONFIG_DIR` value. This is the key architectural fact for Section 6: moving to local execution means CoderFleet would have to start setting *distinct* `CODEX_HOME`/`CLAUDE_CONFIG_DIR` values per account (e.g. `~/.coderfleet/accounts/<name>/.codex`), since there is no longer a container boundary providing the isolation.
- **Per-account-type binary name and login subcommand are already centrally registered** in `AccountTypeSpec` (`account_type_registry.py:1033-1048`), with `login_cli="claude"`, `login_args=["login"]` for Claude (`account_type_registry.py:1069`) and `login_cli="codex"`, `login_args=["login", "--device-auth"]` for Codex (`account_type_registry.py:1085`). This registry is exactly the place a "detect installed host CLIs" feature would slot into, since it is already the single source of truth CoderFleet uses to know each account type's CLI binary name.

## 2. Auth/credential storage location and multi-identity isolation

- **Claude Code, official docs, exact storage locations by OS**: "On macOS, credentials are stored in the encrypted macOS Keychain. On Linux, credentials are stored in `~/.claude/.credentials.json` with file mode `0600`. On Windows, credentials are stored in `%USERPROFILE%\.claude\.credentials.json`... If you've set the `CLAUDE_CONFIG_DIR` environment variable on Linux or Windows, the `.credentials.json` file lives under that directory instead." (`code.claude.com/docs/en/authentication`, "Credential management" → "Storage location"). Note the explicit macOS carve-out: `CLAUDE_CONFIG_DIR` is documented to relocate the credentials file only "on Linux or Windows" — on macOS the credential itself lives in Keychain regardless of `CLAUDE_CONFIG_DIR`, though other config files still move.
- **`CLAUDE_CONFIG_DIR` is *not* documented on Claude Code's own environment-variables reference page** — a full-page search of `code.claude.com/docs/en/env-vars` for the literal string "CLAUDE_CONFIG_DIR" returned no occurrence (WebFetch search of that exact page), and a similar full-page search of `code.claude.com/docs/en/settings` also found no occurrence, only documenting the un-overridden defaults (`~/.claude/settings.json`, `~/.claude.json`). The variable is documented exactly once, on the Authentication page cited above — this is a narrow, specific documentation gap, not an absence of the feature.
- **`CLAUDE_CONFIG_DIR` isolation was empirically verified in this research sandbox, not merely inferred from docs.** Running `claude auth status` unmodified returned `{"loggedIn": true, "authMethod": "claude.ai", ... "email": "zhchxiao1234567@proton.me", ...}` (exit code 0). Running `CLAUDE_CONFIG_DIR=/tmp/rt-claude-test claude auth status` against a freshly created empty directory returned `{"loggedIn": false, "authMethod": "none", "apiProvider": "firstParty"}` (exit code 1), and the CLI created `.claude.json` plus a `backups/` directory under that fresh path. This directly demonstrates that two different `CLAUDE_CONFIG_DIR` values on the same host produce two completely independent, non-clobbering identities — confirmed by direct CLI invocation in this session, temp directories removed afterward.
- **Codex CLI, official docs, exact storage locations**: "`file` stores credentials in `auth.json` under `CODEX_HOME` (defaults to `~/.codex`)." and "Codex caches login details locally in a plaintext file at `~/.codex/auth.json` or in your OS-specific credential store." (`learn.chatgpt.com/docs/auth.md`, credential-storage section). The same page documents a `cli_auth_credentials_store` config key with three values: `file` (writes `auth.json`), `keyring` ("stores credentials in your operating system credential store"), and `auto` ("uses the OS credential store when available, otherwise falls back to `auth.json`") — verbatim from `learn.chatgpt.com/docs/auth.md`.
- **`CODEX_HOME` is officially documented as the override mechanism**: "Codex reads configuration from `$CODEX_HOME/config.toml`... Codex reads configuration from `$CODEX_HOME/config.toml`, and if `CODEX_HOME` is not set it defaults to `~/.codex`... You can override the location with the `CODEX_HOME` environment variable." (`learn.chatgpt.com/docs/config-file/environment-variables`, "Core Locations" section). Unlike Claude Code's `CLAUDE_CONFIG_DIR`, `CODEX_HOME` is a first-class, officially documented environment variable for exactly this purpose.
- **`CODEX_HOME` isolation was also empirically verified in this sandbox.** `codex login status` in the default environment (`CODEX_HOME=/home/byclaw/.codex`, a directory that does not exist here) returned `Error loading configuration: CODEX_HOME points to "/home/byclaw/.codex", but that path does not exist` (exit 1). `CODEX_HOME=/tmp/rt-codex-test codex login status` against a freshly created empty directory returned a clean `Not logged in` (exit 1) rather than an error — demonstrating the CLI scopes its entire config/auth state to whatever `CODEX_HOME` points at, consistent with the doc claim above.
- **Codex's own CLI startup check enforces `CODEX_HOME` existing beforehand**: verbatim CLI output observed in this sandbox: `WARNING: proceeding, even though we could not create PATH aliases: CODEX_HOME points to "/home/byclaw/.codex", but that path does not exist` (from running bare `codex --help`) — this is Codex's own behavior of warning (but still proceeding for `--help`) when `CODEX_HOME` doesn't exist; a real command (e.g. `login status`) hard-fails instead, as shown above. This means a local-execution backend must `mkdir -p` each per-account `CODEX_HOME` directory before invoking Codex, or the invocation errors out.
- **Conclusion for Section 6**: both CLIs support multiple isolated identities on one host via a config-dir override env var (`CLAUDE_CONFIG_DIR` for Claude Code — documented only on the Authentication page, not the env-vars reference page; `CODEX_HOME` for Codex — documented as the primary, first-class mechanism), and this was verified by direct invocation, not just documentation. This is exactly what CoderFleet's own `compose.py`/`scheduler.py` already do today (Section 1) — the only change needed for local execution is to stop hardcoding the *same* path for every account and instead assign each account a distinct host directory value for these two variables.

## 3. Proxy environment variable support

- **Claude Code officially documents standard proxy env var support**, with exact precedence order: "Claude Code respects standard proxy environment variables... Lowercase variants also work, and Claude Code uses the first one that's set in the order `https_proxy`, `HTTPS_PROXY`, `http_proxy`, `HTTP_PROXY`." (`code.claude.com/docs/en/network-config`, "Proxy configuration" → "Environment variables"). The same page documents `NO_PROXY` support (space- or comma-separated, or `"*"` to bypass for all requests) and states explicitly: "Claude Code does not support SOCKS proxies."
- **Claude Code's proxy-env-var reading has a documented scope caveat that matters for CoderFleet's plain-CLI (non-Desktop) invocation model**: "In Claude Desktop sessions where the app manages the provider connection... Claude Code reads them only from managed settings and `~/.claude/settings.json`... In a local, SSH, or WSL Code tab session signed in through claude.ai, the app doesn't manage the connection, and Claude Code reads these variables from every settings scope, like any terminal session" (`code.claude.com/docs/en/network-config`, "mTLS authentication" section, final paragraph). Since CoderFleet invokes `claude -p ...` as a plain terminal/subprocess call (not through Claude Desktop), the unrestricted "reads from every settings scope, like any terminal session" behavior applies — i.e., shell-exported `HTTPS_PROXY` etc. (exactly what `compose.py`/`scheduler.py` inject today) is read normally.
- **Claude Code startup validates the proxy URL and fails fast on a malformed value**: "The one setting it checks at startup is the proxy URL: when it can't parse the value, such as one missing the `http://` scheme, Claude Code stops launch with an error naming the variable to fix." (`code.claude.com/docs/en/network-config`, "Verify your configuration" section).
- **Codex CLI's own official docs pages fetched for this research (`learn.chatgpt.com/docs/config-file/environment-variables`) do not document `HTTP_PROXY`/`HTTPS_PROXY`/`NO_PROXY`/`ALL_PROXY` at all** — a full-page extraction of that page's environment-variable listing surfaced `CODEX_HOME`, `CODEX_SQLITE_HOME`, `CODEX_NON_INTERACTIVE`, `CODEX_INSTALL_DIR`, `CODEX_API_KEY`, `CODEX_ACCESS_TOKEN`, `CODEX_CA_CERTIFICATE`, `SSL_CERT_FILE`, and `RUST_LOG`, but no proxy variables. **This is flagged explicitly as unverified from Codex's own primary docs** — the official reference page does not confirm or deny standard proxy env var support.
- **A live, open `openai/codex` GitHub issue directly evidences that proxy support is inconsistent/in-progress, not confirmed-working, as of this research** — issue #4242, titled "Use proxy environment variables across Codex HTTP clients," verbatim from the issue body: "Codex CLI should automatically honor HTTPS_PROXY, HTTP_PROXY, and ALL_PROXY for every outgoing reqwest client" (a *feature request*, i.e. describing a gap rather than existing behavior), proposing a shared helper `codex_core::default_client::apply_env_proxy`; the issue references PR #3455 and a branch `feat/env-proxy-client` as an in-progress fix, and as of this research the issue's fetched state shows no confirmation that it has been merged/closed. **This is cited as a primary source (the actual GitHub issue text) evidencing an open gap, not as a secondary blog claim** — but whether the specific `codex-cli 0.146.0` installed in this sandbox already includes this fix could not be confirmed from the issue thread alone, and is flagged as unverified.
- **Conclusion for Section 6**: Claude Code's proxy-env-var support is solidly documented and applies to CoderFleet's plain-terminal invocation pattern. Codex's is explicitly *not* confirmed either way from Codex's own primary sources — this is a real open risk for a local-execution backend that relies on `HTTPS_PROXY`/`ALL_PROXY` env vars (as `compose.py`/`scheduler.py` currently do for containers) to route Codex's outbound traffic through the same enforcement point CoderFleet uses today.

## 4. Auto-detection / probing a CLI on the host

- **Claude Code binary name and `--version` output format, verbatim from this sandbox**: `claude --version` → `2.1.220 (Claude Code)`. The official docs confirm this exact format independently: "A working installation prints a version number such as `2.1.211 (Claude Code)`." (`code.claude.com/docs/en/setup`, "Verify your installation" section).
- **Codex binary name and `--version` output format, verbatim from this sandbox**: `codex --version` → `codex-cli 0.146.0` (preceded by the CODEX_HOME warning noted in Section 2, which is printed to stderr/stdout before the version line and would need to be filtered out or tolerated by any host-probe logic).
- **Claude Code documents four install methods with exact commands** (`code.claude.com/docs/en/setup`, "Install Claude Code" tabs): native installer `curl -fsSL https://claude.ai/install.sh | bash` (macOS/Linux/WSL) or `irm https://claude.ai/install.ps1 | iex` (Windows PowerShell); Homebrew `brew install --cask claude-code` (two channel casks: `claude-code` stable, `claude-code@latest`); WinGet `winget install Anthropic.ClaudeCode`; and npm `npm install -g @anthropic-ai/claude-code` (documented separately under "Advanced installation options" → "Install with npm," noting "As of v2.1.198, the npm package requires Node.js 22 or later" and that "The npm package installs the same native binary as the standalone installer"). Native-install binary location: "the native installer manages the launcher at `~/.local/bin/claude` as a symlink into `~/.local/share/claude/versions/`" (same page, "Auto-updates" section).
- **Codex install methods, from the `openai/codex` GitHub `README.md` (fetched via `raw.githubusercontent.com/openai/codex/main/README.md`)**: curl script `curl -fsSL https://chatgpt.com/codex/install.sh | sh` (Mac/Linux); PowerShell `powershell -ExecutionPolicy ByPass -c "irm https://chatgpt.com/codex/install.ps1 | iex"` (Windows); npm `npm install -g @openai/codex`; Homebrew `brew install --cask codex`; and manual binary download from GitHub Releases (e.g. `codex-aarch64-apple-darwin.tar.gz`, `codex-x86_64-unknown-linux-musl.tar.gz`).
- **Both CLIs were found already installed via npm global packages in this sandbox**, confirmed by `npm ls -g --depth=0` showing `├── @anthropic-ai/claude-code@2.1.220` and `├── @openai/codex@0.146.0`, and `which claude` / `which codex` resolving to `/usr/bin/claude` and `/usr/bin/codex` respectively (this sandbox's PATH, not necessarily representative of a fresh host).
- **A basic auto-detection probe is exactly `shutil.which("claude")` / `shutil.which("codex")` followed by a `--version` subprocess call** — this pattern already exists in this codebase for a different binary: `coderfleet/docker_ops.py:31` and `coderfleet/server/docker_mgr.py:17` both call `shutil.which("docker-compose")`, and `coderfleet/data/scripts/coderfleet_usage_status.py:75` calls `shutil.which("codex")` (checking for Codex specifically, inside a container, for a different purpose — usage-status polling). No existing code in this repo currently probes for `claude`/`codex` on the **host** (outside a container) for account-type auto-detection; `account_type_registry.py`'s `login_cli` field (Section 1) would be the natural place to hang such a probe.

## 5. Non-interactive session resume/chaining (host-CLI equivalent of `docker exec ... --resume {native_session_id}`)

- **Claude Code's exact resume flags, verbatim from `claude --help`**: `-c, --continue` — "Continue the most recent conversation in the current directory"; `-r, --resume [value]` — "Resume a conversation by session ID, or open interactive picker with optional search term"; `--session-id <uuid>` — "Use a specific session ID for the conversation (must be a valid UUID)"; `--fork-session` — "When resuming, create a new session ID instead of reusing the original (use with `--resume` or `--continue`)". CoderFleet's own `_build_claude` (`account_type_registry.py:224-239`) uses exactly the `--resume` flag: `resume = f" --resume {shlex.quote(session_id)}" if session_id else ""` (`account_type_registry.py:228`), appended to a `claude -p ...` invocation.
- **Official docs confirm the exact non-interactive resume pattern CoderFleet's containers already use, and how to capture the session ID for later resume**: "If you're running multiple conversations, capture the session ID to resume a specific one: `session_id=$(claude -p "Start a review" --output-format json | jq -r '.session_id')` / `claude -p "Continue that review" --resume "$session_id"`... Run both commands from the same directory: session ID lookup is scoped to the current project directory and its git worktrees." (`code.claude.com/docs/en/headless`, "Continue conversations" section). This project-directory scoping rule is a new constraint relevant to local execution: unlike a container (which has an isolated `/workspace`), a host session's resumability is tied to the actual host directory the command ran in.
- **CoderFleet's own session-ID extraction logic** (`_extract_claude`, `account_type_registry.py:920-930`) scans task output for JSON lines and returns `d["session_id"]` — this matches the `--output-format json`/`stream-json` shape documented above.
- **Codex's exact resume flags, verbatim from `codex --help` / `codex exec --help` / `codex resume --help`**: top-level `resume` subcommand — "Resume a previous interactive session (picker by default; use `--last` to continue the most recent)"; under `codex resume`, `[SESSION_ID]` argument — "Session id (UUID) or session name. UUIDs take precedence if it parses. If omitted, use `--last` to pick the most recent recorded session"; and `--last` — "Continue the most recent session without showing the picker". For non-interactive use, CoderFleet's own `_build_codex` (`account_type_registry.py:242-257`) uses `codex exec resume {shlex.quote(session_id)} --json --skip-git-repo-check{danger}{imgs}` when a `session_id` is present (`account_type_registry.py:250`), confirmed by `codex exec --help`'s own `Commands: resume  Resume a previous session by id or pick the most recent with --last`.
- **CoderFleet's own thread-ID extraction for Codex** (`_extract_codex`, `account_type_registry.py:934-944`) looks for a JSON event with `"type": "thread.started"` and returns `d["thread_id"]` — i.e. Codex's `--json` streaming output emits a `thread_id`, which is what gets passed back into `codex exec resume <thread_id>` for the next task in a chain.
- **Conclusion for Section 6**: both CLIs' native resume mechanics (`claude -p --resume <session_id>`, `codex exec resume <session_id>`) are pure CLI flags with no dependency on Docker — they would work identically as a plain host subprocess, provided the working directory (Claude Code's project-directory scoping) and `CODEX_HOME`/`CLAUDE_CONFIG_DIR` (Section 2) are set up per-account/per-conversation consistently between the initial task and every resumed task.

## 6. Sandboxing / permission model for local (non-containerized) execution

- **Claude Code has an opt-in, OS-level sandboxed Bash tool, separate from permission modes, and it is off by default.** "The Bash sandbox lets Claude run most shell commands without stopping to ask permission. Instead of approving each command, you define which files and network domains commands can touch, and the operating system enforces that boundary for every Bash command and its child processes." (`code.claude.com/docs/en/sandboxing`, intro). Enforcement mechanism, verbatim: "**macOS**: uses Seatbelt for sandbox enforcement. **Linux**: uses bubblewrap for isolation. **WSL2**: uses bubblewrap, same as Linux." (same page, "OS-level enforcement" section). Defaults: "By default, commands inside the sandbox can write only to the working directory and the session temp directory... no domains are pre-allowed by default. The first time a command needs a new domain, Claude Code prompts for approval." (same page, "Get started" step 3 and "Network isolation" section).
- **The sandbox has a documented silent-fallback failure mode that is directly relevant to trusting it for isolation**: "By default, if the sandbox cannot start because dependencies are missing or the platform is unsupported, Claude Code shows a warning and runs commands **without sandboxing**. To make this a hard failure instead, set `sandbox.failIfUnavailable` to `true`." (`code.claude.com/docs/en/sandboxing`, Warning callout under "Get started"). This means a naive local-execution deployment that assumes "the sandbox is protecting me" could silently run fully unsandboxed if `bubblewrap`/`socat` aren't installed on the host, unless `failIfUnavailable` is explicitly configured.
- **Claude Code's own docs state the sandbox is not a complete isolation boundary, in a dedicated "Limitations" section, verbatim**: "Sandboxing reduces risk but is not a complete isolation boundary. Review the limitations below before relying on it as a hard security control." followed by specific caveats including that the built-in network proxy "does not terminate or inspect TLS on outbound traffic, so the contents of encrypted connections are not examined," and a `docker` compatibility note: "**`docker` commands fail**: `docker` is incompatible with the sandbox. Add `docker *` to `excludedCommands` to run it outside the sandbox." (`code.claude.com/docs/en/sandboxing`, "Troubleshooting" and "Limitations" sections). The `--dangerously-skip-permissions` flag used by CoderFleet's own `auto=True` task path (`account_type_registry.py:227`: `perm = "--dangerously-skip-permissions" if auto else "--permission-mode acceptEdits"`) is documented to bypass the regular permission flow entirely and is explicitly scoped by Anthropic's own docs to container/VM use: verbatim from `claude --help`, `--dangerously-skip-permissions`: "Bypass all permission checks. Recommended only for sandboxes with no internet access." — i.e. Anthropic's own guidance already assumes this flag is used inside an isolated environment, which is exactly the assumption a local-execution mode would break unless the built-in Bash sandbox (a separate, opt-in feature) is also turned on.
- **Codex has a first-class `--sandbox` flag with three explicit policy levels, verbatim from `codex exec --help`**: `-s, --sandbox <SANDBOX_MODE>` — "Select the sandbox policy to use when executing model-generated shell commands [possible values: read-only, workspace-write, danger-full-access]". CoderFleet's own `_build_codex` already picks between the two extremes based on its own `auto` flag: `sandbox = "danger-full-access" if auto else "workspace-write"` (`account_type_registry.py:252`), plus a separate override `--dangerously-bypass-approvals-and-sandbox` when a resumed session runs in `auto` mode (`account_type_registry.py:246`).
- **`--dangerously-bypass-approvals-and-sandbox`'s own `--help` text explicitly assumes external (e.g. container) sandboxing, verbatim from `codex --help`**: "Skip all confirmation prompts and execute commands without sandboxing. EXTREMELY DANGEROUS. Intended solely for running in environments that are externally sandboxed" — this is the single most direct piece of evidence in this research that Codex's own maintainers assume this flag (which is exactly what CoderFleet passes for `auto`-mode resumed Codex tasks) is used inside something like a Docker container, not on a bare host.
- **Codex's sandbox enforcement mechanism, from Codex's own official docs**: "On macOS, sandboxing works out of the box using the built-in Seatbelt framework." and on Linux/WSL2 "the implementation uses bubblewrap (user namespace isolation), with a fallback to a bundled helper, but that helper requires support for unprivileged user namespace creation... on some Linux distributions, Codex may still warn that it can't create the needed user namespace" (`learn.chatgpt.com/docs/sandboxing`). This is essentially the same OS-level primitive (Seatbelt on macOS, bubblewrap on Linux) that Claude Code's sandbox documentation describes above — both CLIs converge on the same two host isolation mechanisms rather than each building something bespoke.
- **Codex's approval-policy flag, verbatim from `codex --help`**: `-a, --ask-for-approval <APPROVAL_POLICY>` — "Configure when the model requires human approval before executing a command," with three documented values: `untrusted` ("Only run 'trusted' commands (e.g. ls, cat, sed) without asking for user approval. Will escalate to the user if the model proposes a command that is not in the 'trusted' set"), `on-request` ("The model decides when to ask the user for approval"), `never` ("Never ask for user approval. Execution failures are immediately returned to the model"). CoderFleet's own `_build_codex` does not set `--ask-for-approval` at all for either `auto` or non-`auto` runs (`account_type_registry.py:242-257`) — approval behavior is controlled entirely through the `--sandbox`/`--dangerously-bypass-approvals-and-sandbox` combination described above, and this research could not confirm Codex's implicit default `--ask-for-approval` value when the flag is omitted (the fetched `learn.chatgpt.com/docs/config-file/config-reference.md` page explicitly does not document a default value for either `sandbox_mode` or `approval_policy` when unspecified — flagged here as unverified rather than guessed).
- **Conclusion for Section 6**: neither CLI's default behavior assumes host isolation is absent — both explicitly gate their most permissive/no-prompt modes with language that assumes an external sandbox (container/VM) already exists, and CoderFleet's own account-type registry already invokes exactly those most-permissive modes (`--dangerously-skip-permissions`, `--dangerously-bypass-approvals-and-sandbox`) whenever a task runs with `auto=True`. Each CLI does ship its own opt-in, real OS-level sandbox (Seatbelt/bubblewrap) that could substitute for the container boundary, but for Claude Code it is off by default and silently falls back to unsandboxed execution if dependencies are missing (unless `failIfUnavailable` is set), and for Codex the closest equivalent (`--sandbox workspace-write`/`read-only`) is already partially wired into CoderFleet's non-auto path but is explicitly *not* used for `auto`-mode tasks today.

## Synthesis (analysis)

*Everything below is my own analysis, not a sourced fact from an external doc/repo/CLI. It applies the facts in sections 1–6 above against CoderFleet's own documented invariants in `/workspace/CLAUDE.md`.*

**A "local" execution backend is structurally feasible without a rewrite, because the `ContainerRuntime` seam (Section 1) already separates "what to run" from "how to launch it" — but it is not a drop-in, because two hardcoded `docker exec` call sites and every account's fixed `CODEX_HOME`/`CLAUDE_CONFIG_DIR` path would have to change.** Concretely, supporting local execution would mean: (1) adding a `LocalRuntime` class implementing the same 4-method `ContainerRuntime` Protocol (`run`/`exec`/`is_running`/`remove` — `runtime.py:57-72`), where `run`/`exec` call `asyncio.create_subprocess_exec(*command, env=merged_env, cwd=project_root)` directly instead of prefixing `docker run`/`docker exec`; (2) routing the two orphaned direct-`docker`-exec call sites (`scheduler.py:3186-3195` and `scheduler.py:3234-3239`) through `self.runtime.exec(...)` so they, too, respect the injected runtime — today they would silently keep shelling into Docker even if the scheduler's main runtime were swapped to `LocalRuntime`, which is exactly the kind of "half-wired" gap CLAUDE.md's cross-cutting invariants call out; (3) giving each `Account` a per-account host directory for `CODEX_HOME`/`CLAUDE_CONFIG_DIR` (e.g. derived from `workspace_dir / "accounts" / acc.name / ".codex"` and `.../.claude`) instead of the single hardcoded `/home/byclaw/.codex` / `/home/byclaw/.claude` container-internal paths `compose.py`/`scheduler.py` use today, since without a container boundary those two env vars are the *only* isolation mechanism (Section 2) — and per Codex's own startup check, that directory must exist (`mkdir -p`) before Codex's first invocation or the command errors out.

**A new `AccountRuntime` or `RunMode` field (`local | container`) is a config-model change that must be end-to-end wired in the same change it's added, per CLAUDE.md's field-wiring invariant** — it is not enough to add `runtime: Literal["local", "container"] = "container"` to `Account` in `models.py`; the same PR must (a) make `Scheduler` pick `DockerRuntime()` vs. a new `LocalRuntime()` per-account rather than once globally at `Scheduler.__init__` (today `self.runtime` is a single scheduler-wide instance, `scheduler.py:109` — a mixed fleet with some `local` and some `container` accounts needs per-task runtime selection, not per-scheduler), (b) update `_get_account_image`/mount-building logic to skip entirely for `local` accounts (there is no image, no `mounts`, no `network` — Section 1's `ContainerSpec` dataclass fields `image`/`mounts`/`network` are all Docker-specific and simply don't apply), and (c) surface the new field through both the Web UI account-add form and the `coderfleet account add ... --proxy relay|off` CLI flag pattern (`CLAUDE.md`'s CLI/Web-UI-parity invariant), e.g. `coderfleet account add <name> TYPE=claude --runtime local`.

**Proxy enforcement is the single biggest open risk, and it is asymmetric between the two CLIs.** Claude Code's proxy-env-var handling is solidly documented for CoderFleet's exact invocation pattern (plain `claude -p ...` subprocess, not Claude Desktop — Section 3), so injecting `HTTPS_PROXY`/`ALL_PROXY`/`NO_PROXY` into the subprocess's `env=` dict (instead of into a container's `docker run -e`) should carry over directly. Codex's proxy support could not be confirmed from Codex's own primary docs, and a live upstream GitHub issue (#4242) explicitly frames "honor `HTTPS_PROXY`/`HTTP_PROXY`/`ALL_PROXY` for every outgoing client" as an open feature request rather than settled behavior (Section 3). Today, CoderFleet's entire network-isolation invariant — "containers join an `internal: true` Docker network; they cannot reach the public internet directly... All traffic is forced through a `coderfleet-proxy-relay` container" (`CLAUDE.md`, "Network isolation") — is enforced at the Docker network layer, not by trusting the CLI to respect an env var. Local execution removes that network-layer backstop entirely: if a `local`-runtime Codex task's HTTP client silently ignores `HTTPS_PROXY` for some request path (as the open issue suggests may still happen for some of Codex's HTTP clients), that account's traffic would egress directly from the host with no relay, no matter what env vars the scheduler sets — a silent violation of the account/proxy-isolation invariant that would not be immediately visible to the operator (in tension with CLAUDE.md's "never silently fall back" cross-cutting rule, applied here to network egress rather than data references). Before shipping `--proxy relay` for `local`-runtime accounts, this would need either host-level enforcement (e.g. a per-account network namespace, or an OS firewall rule scoping that account's OS user/process group to the relay) or an explicit, documented limitation that `--proxy relay` for `local` accounts is Claude-only until Codex's proxy behavior is verified against a specific pinned Codex CLI version.

**Isolation loss is real but narrower than "no isolation at all," because both CLIs already ship an opt-in OS-level sandbox that substitutes some of what Docker was providing — provided it's turned on explicitly, since both default to off/permissive in exactly the modes CoderFleet already uses for `auto=True` tasks.** Section 6 shows Claude Code's Bash sandbox (Seatbelt/bubblewrap) and Codex's `--sandbox`/`--ask-for-approval` flags are real, OS-enforced boundaries, not merely permission prompts — but CoderFleet's own `auto=True` path already reaches for each CLI's *most* permissive flag (`--dangerously-skip-permissions` for Claude, `--dangerously-bypass-approvals-and-sandbox` for Codex-with-resume), and both flags' own `--help`/docs text frames them as safe only "in sandboxes with no internet access" / "environments that are externally sandboxed" — i.e., safe specifically because a Docker container was assumed to be doing the actual containment. A local-execution `auto=True` task using these same flags on a bare host would run with no OS-level containment at all unless CoderFleet additionally and explicitly enables Claude Code's `sandbox.enabled` setting (with `failIfUnavailable: true`, since it silently disables itself otherwise — Section 6) or Codex's `--sandbox workspace-write` (dropping the `--dangerously-bypass-approvals-and-sandbox` override for local accounts specifically). This is a policy decision CoderFleet would need to make explicitly per account, not something that falls out "for free" from switching the runtime.

**Credential collision is the most tractable of the four risks, because both CLIs already support per-account isolation via a documented (Codex) or empirically-confirmed (Claude) config-dir override, and CoderFleet's own container conventions already use the identical mechanism today, just pinned to one shared value instead of per-account values.** No architecture change is needed here beyond what's described above (per-account `CODEX_HOME`/`CLAUDE_CONFIG_DIR` directories, created before first use) — this is the one area where "what would have to change" is a small, mechanical change rather than an open design question, and Section 2's empirical tests in this very sandbox demonstrate it works exactly as needed (two different config-dir values on one host, zero clobbering) before any code is written.

**Recommendation**: local execution is worth building as an additive `runtime: local | container` option on `Account`, gated by (1) routing the two orphaned `docker exec` call sites through the existing `ContainerRuntime` seam first (a prerequisite cleanup, independent of local execution, that removes a latent bug where swapping runtimes wouldn't fully take effect), (2) shipping Claude-only first if timeline pressure demands narrowing scope, since Claude Code's proxy behavior is confirmed and Codex's is not, (3) requiring the account's own OS-level sandbox (Claude Code `sandbox.enabled`, Codex `--sandbox workspace-write`) to be turned on for any `local`-runtime account running with `auto=True`, since that flag's own upstream documentation assumes external containment CoderFleet would no longer be providing, and (4) treating "no host-level network enforcement for `local`+`relay` accounts" as an explicit, documented limitation (or blocking that combination outright) until Codex's proxy-respecting behavior is verified against the specific pinned CLI version CoderFleet ships.
