Research date: 2026-07-19. ## 1. Sourced facts

### 1. Architecture — what deepagents actually provides

- **Package layout**: `langchain-ai/deepagents` is a monorepo. The library discussed here is the core package at `libs/deepagents/`, a Python package `deepagents` (there are sibling packages `libs/cli`, `libs/acp`, `libs/code`, `libs/evals`, `libs/partners`, `libs/talon` that are out of scope). Source: `https://api.github.com/repos/langchain-ai/deepagents/contents/libs` (GitHub Contents API).

- **Primary entry point**: `create_deep_agent()`, defined in `libs/deepagents/deepagents/graph.py`. Its own docstring states: *"By default, this agent has access to the following tools: `write_todos`: manage a todo list; `ls`, `read_file`, `write_file`, `edit_file`, `glob`, `grep`: file operations; `execute`: run shell commands; `task`: call subagents."* (`libs/deepagents/deepagents/graph.py`, docstring of `create_deep_agent`, fetched via `raw.githubusercontent.com/langchain-ai/deepagents/main/libs/deepagents/deepagents/graph.py`).

- **Planning tool**: `write_todos` is supplied by `TodoListMiddleware`, imported directly from LangChain core (`from langchain.agents.middleware import HumanInTheLoopMiddleware, InterruptOnConfig, TodoListMiddleware` — `graph.py` import block) and is always the first middleware appended to both the main agent and every subagent's middleware stack (`deepagent_middleware: list[...] = [TodoListMiddleware()]` in `graph.py`). It is not deepagents-authored code — it's a re-used LangChain middleware — but deepagents wires it in unconditionally.

- **Sub-agent spawning**: `SubAgentMiddleware` (`libs/deepagents/deepagents/middleware/subagents.py`) adds a `task` tool that spawns "ephemeral inline sub-agents with inherited state" — exact wording from the package's own `THREAT_MODEL.md`, Components table, row C9: *"Adds a `task` tool that spawns ephemeral inline sub-agents with inherited state ... framework-controlled ... Yes (always added by `create_deep_agent`)"*. Three subagent forms are supported per the `subagents` parameter docstring in `graph.py`: `SubAgent` (declarative, synchronous, invoked through `task`), `CompiledSubAgent` (pre-compiled `runnable`, also exposed via `task`), and `AsyncSubAgent` (remote/background subagents routed to `AsyncSubAgentMiddleware`, identified by presence of a `graph_id` field — `libs/deepagents/deepagents/middleware/async_subagents.py`). If no subagent named `general-purpose` is supplied, a default general-purpose subagent is auto-added (`graph.py`, lines building `general_purpose_spec`).

- **Virtual filesystem**: `FilesystemMiddleware` (`libs/deepagents/deepagents/middleware/filesystem.py`) is always added (`_REQUIRED_MIDDLEWARE` tuple in `graph.py` includes `(FilesystemMiddleware, ())`) and backs every built-in file tool (`ls`, `read_file`, `write_file`, `edit_file`, `delete`, `glob`, `grep`, `execute` — the literal type alias `FsToolName = Literal["ls", "read_file", "write_file", "edit_file", "delete", "glob", "grep", "execute"]` at `libs/deepagents/deepagents/middleware/filesystem.py:1100`). The filesystem is backend-pluggable: `StateBackend` (default, in-memory/ephemeral LangGraph state), `FilesystemBackend` (real host filesystem), `LocalShellBackend`, `StoreBackend` (LangGraph `BaseStore`), `CompositeBackend` (path-prefix routing across multiple backends) — all listed and described in `libs/deepagents/deepagents/backends/` (`__init__.py`, `filesystem.py`, `local_shell.py`, `store.py`, `composite.py`, `sandbox.py`, `state.py`, `context_hub.py`, `langsmith.py`). README's own wording: *"Filesystem — read, write, edit, or search over pluggable local, sandboxed, or remote backends"* (`libs/deepagents/README.md`).

- **Context management**: README states *"Context management — summarize long threads and offload tool outputs to disk"* (`libs/deepagents/README.md`, Features list). Implemented via `SummarizationMiddleware`/`create_summarization_middleware` (`libs/deepagents/deepagents/middleware/summarization.py`), always appended to both main-agent and subagent middleware stacks in `graph.py`.

- **Skills system**: `SkillsMiddleware` (`libs/deepagents/deepagents/middleware/skills.py`), opt-in via the `skills=` parameter, loads `SKILL.md` files and injects metadata into the system prompt (per `THREAT_MODEL.md` Components table, row C8).

- **Prompt structure**: `create_deep_agent`'s `system_prompt` parameter accepts a plain string/`SystemMessage` or a `SystemPromptConfig` TypedDict (`graph.py`, class `SystemPromptConfig`) with keys `prefix`, `base`, `suffix`. Final assembly order is `prefix → base (default BASE_AGENT_PROMPT constant, ~40 lines, defined verbatim in `graph.py`) → suffix → HarnessProfile.system_prompt_suffix`, joined by blank lines (`_assemble_prompt_parts` function, `graph.py`).

### 2. Runtime requirements

- **Python version**: `requires-python = ">=3.11,<4.0"` — `libs/deepagents/pyproject.toml`, `[project]` section, fetched directly via `raw.githubusercontent.com`.
- **Package version pinned/observed**: `version = "0.6.12"` in the same `pyproject.toml`; `CHANGELOG.md` confirms `0.6.12` was released 2026-06-25 (`libs/deepagents/CHANGELOG.md`, top entry).
- **Development status classifier**: `"Development Status :: 4 - Beta"` — `libs/deepagents/pyproject.toml`, `classifiers` list. This is the maintainers' own PyPI trove classifier, not third-party speculation.
- **Hard dependencies** (from `pyproject.toml` `[project.dependencies]`): `langchain>=1.3.12,<2.0.0`, `langchain-core>=1.4.9,<2.0.0`, `langchain-anthropic>=1.4.8,<2.0.0`, `langchain-google-genai>=4.2.7,<5.0.0`, `langsmith>=0.9.3`, `wcmatch>=10.1`. Note `langchain-anthropic` and `langchain-google-genai` are **unconditional** dependencies (not optional extras) — Anthropic and Google Gemini support ships in the base install. `langchain-aws` (Bedrock) is an optional extra: `aws = ["langchain-aws>=1.6.2,<2.0.0"]`.
- **Runs standalone as a library, no server required**: `THREAT_MODEL.md` System Overview states explicitly: *"It is intended for use in developer-facing CLI tools, research pipelines, and application backends where users control the execution environment. It does **not** run a server itself — it compiles a graph that user application code invokes."* (`libs/deepagents/THREAT_MODEL.md`, "System Overview" section). A LangGraph server/deployment is only needed for the *opt-in* `AsyncSubAgent` remote/background-subagent feature, which talks to "user-configured remote LangGraph server URLs" via the LangGraph SDK (`THREAT_MODEL.md`, Assumption 7; also `middleware/async_subagents.py`).
- **Model providers supported**: README FAQ, verbatim: *"Any model that supports tool calling works — frontier APIs (OpenAI, Anthropic, Google), open-weight models hosted on providers like Baseten or Fireworks, and self-hosted models via Ollama, vLLM, or llama.cpp. Use any LangChain chat model."* (`libs/deepagents/README.md`, FAQ section "Does this work with open-weight or local models?").
- **Anthropic/Claude support out of the box — confirmed in actual code, not just docs**: `graph.py` imports `from langchain_anthropic import ChatAnthropic` at module scope (a hard, non-lazy import, consistent with `langchain-anthropic` being a required dependency), and the internal default-model builder is `def _build_default_model() -> ChatAnthropic: return ChatAnthropic(model_name="claude-sonnet-4-6")`. The public deprecated fallback `get_default_model()` calls this same builder and its docstring says: *"Requires `ANTHROPIC_API_KEY` to be set in the environment."* (both in `graph.py`). Also `AnthropicPromptCachingMiddleware` (`from langchain_anthropic.middleware import AnthropicPromptCachingMiddleware`) is unconditionally appended to every middleware stack, main and subagent (`_append_prompt_caching_middleware` function, `graph.py`) — it "no-ops for non-Anthropic models," meaning Claude gets first-class, zero-configuration prompt-caching support that other providers only get if their own optional middleware package is installed.

### 3. Extension points for custom tools

- **Exact constructor signature** (from `libs/deepagents/deepagents/graph.py`, `def create_deep_agent(...)`, quoted verbatim):

  ```python
  def create_deep_agent(
      model: str | BaseChatModel | None = None,
      tools: Sequence[BaseTool | Callable | dict[str, Any]] | None = None,
      *,
      system_prompt: str | SystemMessage | SystemPromptConfig | None = None,
      middleware: Sequence[AgentMiddleware[StateT_co, ContextT]] = (),
      subagents: Sequence[SubAgent | CompiledSubAgent | AsyncSubAgent] | None = None,
      skills: list[str] | None = None,
      memory: list[str] | None = None,
      permissions: list[FilesystemPermission] | None = None,
      backend: BackendProtocol | BackendFactory | None = None,
      interrupt_on: dict[str, bool | InterruptOnConfig] | None = None,
      response_format: ResponseFormat[ResponseT] | type[ResponseT] | dict[str, Any] | None = None,
      state_schema: type[DeepAgentState] | None = None,
      context_schema: type[ContextT] | None = None,
      checkpointer: Checkpointer | None = None,
      store: BaseStore | None = None,
      debug: bool = False,
      name: str | None = None,
      cache: BaseCache | None = None,
  ) -> CompiledStateGraph[...]
  ```

- **`tools=` parameter type**: `Sequence[BaseTool | Callable | dict[str, Any]] | None`. A custom tool can be a plain Python callable, a `dict` tool spec, or a `langchain_core.tools.BaseTool` instance (i.e. anything built with LangChain's `@tool` decorator, which produces a `BaseTool`). The docstring is explicit: *"tools: Additional tools the agent should have access to. These are merged with the built-in tool suite ... Passing tools here is additive — it never removes a built-in."* (`graph.py`, `create_deep_agent` docstring, `tools` arg). README confirms with the same framing: *"Tools — bring your own functions or any MCP server."* (`libs/deepagents/README.md`).
- **Concrete usage example from the README** (quoted verbatim, `libs/deepagents/README.md`):
  ```python
  from deepagents import create_deep_agent

  agent = create_deep_agent(
      model="openai:gpt-5.5",
      tools=[my_custom_tool],
      system_prompt="You are a research assistant.",
  )
  result = agent.invoke({"messages": "Research LangGraph and write a summary"})
  ```
  This means a tool such as one that shells into `docker exec` or calls a CoderFleet scheduler function would be an ordinary Python function (optionally `@tool`-decorated for name/description control) passed in the `tools` list — no special deepagents-specific tool-registration API exists beyond what `langchain_core.tools.BaseTool` / plain callables already provide.
- **Custom middleware as a second extension axis**: `middleware: Sequence[AgentMiddleware[StateT_co, ContextT]] = ()` lets a caller inject arbitrary `AgentMiddleware` (LangChain's own middleware base class) into a fixed slot in the assembly order — after the base stack, before the profile/prompt-caching/memory tail (documented ordering list in the `middleware` docstring entry, `graph.py`).
- **Custom backend as a third extension axis**: `backend: BackendProtocol | BackendFactory | None`. A caller can implement `BackendProtocol` (`libs/deepagents/deepagents/backends/protocol.py`, `class BackendProtocol(abc.ABC)`) or `SandboxBackendProtocol` (same file, `class SandboxBackendProtocol(BackendProtocol)`) to route filesystem/`execute` calls into arbitrary infrastructure — e.g., a hypothetical CoderFleet backend that maps virtual paths to `docker exec cat`/`docker cp` calls instead of the local disk.

### 4. Built-in filesystem access, human-in-the-loop approval, and sandboxing

- **Filesystem access control (`FilesystemPermission`)**: Defined as a `@dataclass` in `libs/deepagents/deepagents/middleware/filesystem.py` (line 254 in the fetched source):
  ```python
  @dataclass
  class FilesystemPermission:
      operations: list[FilesystemOperation]
      paths: list[str]
      mode: Literal["allow", "deny", "interrupt"] = "allow"
  ```
  Rules are evaluated in declaration order, first match wins, and an unmatched call defaults to `"allow"` (`_check_fs_permission` function in the same file: `return "allow"` at the end when no rule matches). Passed to `create_deep_agent(permissions=[...])`. `mode="interrupt"` auto-installs `HumanInTheLoopMiddleware` and merges the generated `interrupt_on` entries with any explicit `interrupt_on=` argument (`_merge_fs_interrupt_on` and `_build_interrupt_on_from_permissions` in `graph.py`; also stated in the `create_deep_agent` docstring's `permissions` arg description).
- **Human-in-the-loop**: `interrupt_on: dict[str, bool | InterruptOnConfig] | None` parameter wires directly into `HumanInTheLoopMiddleware`, imported from `langchain.agents.middleware` (i.e. this is LangChain-core functionality, not deepagents-original code) — `from langchain.agents.middleware import HumanInTheLoopMiddleware, InterruptOnConfig, TodoListMiddleware` (`graph.py` import block). It is **opt-in only**: `HumanInTheLoopMiddleware` is appended to the middleware stack solely `if main_interrupt_on is not None:` (`graph.py`). Without an explicit `interrupt_on` argument or an `"interrupt"`-mode `FilesystemPermission` rule, no approval gate exists — every tool call executes immediately.
- **Sandboxing — this is NOT what the name implies; verify carefully.** The package provides a `SandboxBackendProtocol` (`libs/deepagents/deepagents/backends/protocol.py`, `class SandboxBackendProtocol(BackendProtocol)`) that adds an `execute()`/`aexecute()` method contract, and a `BaseSandbox` abstract base class (`libs/deepagents/deepagents/backends/sandbox.py`) that "implements all inherited file operations by delegating to `execute()`" (per its own docstring, quoted in `SandboxBackendProtocol`'s docstring). **However, `deepagents` itself does not ship any actual process/OS isolation.** The package's own `THREAT_MODEL.md` states this directly:
  - Assumption 5: *"Users who require isolation for untrusted workloads are expected to extend `BaseSandbox` or use container/VM-level sandboxing — **the library does not provide OS-level process isolation.**"*
  - The default backend, `StateBackend`, does not implement `SandboxBackendProtocol` at all, so the `execute` (shell) tool is filtered out entirely unless the caller opts into a sandbox-capable backend: *"The `execute` tool is filtered out by `FilesystemMiddleware` when the backend does not implement `SandboxBackendProtocol`"* (`THREAT_MODEL.md`, "Rationale" section under "Out-of-Scope Threats").
  - The one backend that does allow real shell execution locally, `LocalShellBackend`, is explicitly documented as dangerous: it runs `subprocess.run(shell=True)` with **zero command validation** beyond a non-empty-string check (Threat T3, `THREAT_MODEL.md`: *"`LocalShellBackend.execute` passes the LLM-generated command string directly to `subprocess.run(shell=True)`... Zero validation on command content beyond a non-empty string check. Commands execute with the process owner's full permissions."*). Even with `virtual_mode=True` restricting file-tool paths, "the shell bypasses `_resolve_path`" entirely (Threat T6). "Sandbox" backends that call out to genuinely isolated infrastructure (containers, VMs, remote hosts) are things a *user* must supply by implementing the protocol against real infrastructure — deepagents ships the interface, not the isolation.
  - README's own framing under a section literally titled "Security": *"Deep Agents follows a 'trust the LLM' model. The agent can do anything its tools allow. Enforce boundaries at the tool/sandbox level, not by expecting the model to self-police."* (`libs/deepagents/README.md`, "🔒 Security" section, quoted verbatim).

## Synthesis (analysis)

*Everything below is my own analysis, not sourced fact from the deepagents repository. It applies the facts in sections 1–5 above against CoderFleet's own documented invariants in `/workspace/CLAUDE.md`.*

**Would a deepagents sub-agent naturally respect CoderFleet's invariants if it called into `scheduler.py` or edited `accounts.conf`/`projects.conf` directly? No — every such tool would need a wrapper, and the gap is structural, not incidental.** Section 3 confirms the *only* way to give deepagents a custom capability is to hand it a plain Python callable or `BaseTool` in the `tools=` list; deepagents imposes no constraint on what that function does internally, how it reads/writes state, or whether it's transactional — that responsibility is entirely the tool author's, exactly as CoderFleet's own `_advance_offset`/`notify_task` incident (`b315ea7`) proved can go wrong even for a team that already knows the single-synchronous-read-modify-write rule. Nothing in deepagents' filesystem/backend layer (section 4) enforces atomic writes to *external* state — `FilesystemPermission` and `BackendProtocol` only govern deepagents' *own* virtual filesystem (`StateBackend`/`FilesystemBackend`/etc.), not arbitrary calls a custom tool makes into `coderfleet/server/scheduler.py` or `docker exec`. So if a tool were written as "read `accounts.conf`, let the LLM reason about it in the response, then a later tool call writes the mutated file back," that is precisely the read-then-later-write race pattern CLAUDE.md's cross-cutting invariant forbids — and deepagents has no mechanism to prevent an agent tool author from writing it that way, because the LLM's multi-turn tool-calling loop is inherently a sequence of separate function invocations with model reasoning (and possibly parallel subagent execution, see `SubAgentMiddleware` in section 1) interleaved between them. The fix is the same one CoderFleet already uses: any tool exposed to a deepagents agent that needs to mutate `accounts.conf`, `projects.conf`, or task/conversation JSON must be a thin wrapper around a single call to an existing single-writer function (`scheduler.conversation_queue_full()`-style, or a hypothetical `scheduler.apply_account_change(...)` that does its own load→mutate→save atomically) — never "give the agent read_file/write_file on the conf files directly," which section 4 confirms is exactly what `FilesystemPermission`/`FilesystemBackend` would do if pointed at those paths.

Three more invariant-specific frictions are worth flagging. First, **account/container/proxy isolation**: deepagents' default `execute` shell tool, per section 4's Threat T3 and T6, passes LLM-generated commands to `subprocess.run(shell=True)` with no command validation and (per T6) bypasses even `virtual_mode` path restrictions — if this were wired to `docker exec` without a wrapper enforcing "only this one project's container, only these commands," a prompt-injection-compromised agent (Threat T2, subagent `description` propagation) could plausibly reach across the account/container boundary CoderFleet exists to enforce; the isolation would have to be re-implemented entirely in the custom tool, not inherited from deepagents. Second, **CLI/Web UI parity**: deepagents is a Python-embeddable library with no server of its own (confirmed in section 2 — "It does not run a server itself"), so embedding it is architecturally neutral on this axis, but only if CoderFleet's own integration exposes any deepagents-agent-triggered action through both `coderfleet <noun> <verb>` and a REST endpoint, exactly as it must for any other feature — deepagents gives no help or hindrance here, the discipline is 100% on CoderFleet's side. Third, **maturity**: section 5's `Development Status :: 4 - Beta` classifier, the library's own pre-1.0 status, the weekly patch cadence with export-breaking changes, and the maintainers' own words that the threat model is "experimental... not an authoritative security reference" argue against adopting it for anything that can silently corrupt state a real user depends on to resume work — CoderFleet's third North Star priority.

**Recommendation: don't embed deepagents as a general autonomous config-management agent today; if pursued at all, embed it only behind a narrow, wrapper-gated integration pattern, not as a direct operator over `scheduler.py`/`*.conf`.** Concretely: (1) never grant it `FilesystemPermission`/`FilesystemBackend` access to `accounts.conf`, `projects.conf`, or any `tasks/*.json`/`conversations/*.json`/`telegram_state.json` file directly — those must stay behind existing single-writer Python functions exposed as narrow, purpose-built tools (e.g. a `propose_account_change(name, type, ...)` tool that validates and calls a real `scheduler`-layer function, never a raw file-write tool); (2) never wire the built-in `execute` shell tool to `docker exec` without a wrapper that hard-codes the target container/account and rejects cross-project commands, since deepagents explicitly disclaims providing that isolation itself; (3) treat any state-mutating tool call as `interrupt_on`-gated (human-in-the-loop) by default until CoderFleet has enough operational track record to trust it unattended, given the library's own "trust the LLM" security posture and beta status; and (4) if adopted, its capability must ship through the same `coderfleet <noun> <verb>` CLI surface as everything else, not as a Web-UI-only "agent chat" feature. Given the amount of custom wrapper-writing this requires just to reach parity with invariants CoderFleet already enforces by convention in hand-written scheduler code, the marginal benefit of deepagents' harness (planning/todo list, sub-agent delegation, context summarization) over simply writing a smaller, purpose-built LangChain `create_agent` call — or no LLM-driven orchestration layer at all for config mutations — is not obviously worth the added dependency surface (`langchain`, `langchain-core`, `langchain-anthropic`, `langchain-google-genai`, `langsmith`, pinned to a pre-1.0 moving target) and the security review burden of auditing every tool for the read-then-write race pattern by hand.
